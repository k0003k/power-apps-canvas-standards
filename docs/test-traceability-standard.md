# Power Apps テスト・トレーサビリティ標準

作成日：2026-08-06  
改訂日：2026-08-07（BFCを業務要件起点の上流成果物として再定義し、成果物作成順序を更新）

## 0. 目的

本標準は、業務要件、BFC、ユースケース、機能、データフロー、SharePointスキーマ、Test Specification、Test Caseおよび変更差分の関係を、AIと人間が追跡できる状態にするための成果物と管理方法を定める。

新規設計または業務要件からテスト設計を行う場合、原則として以下の順に成果物を作成する。

```text
業務要件
  ↓
BFC 初版
  ↓
ユースケース間依存関係表
  ↓
機能一覧
  ↓
BFC 更新（正式な機能IDを紐付け）
  ↓
データフロー対応表
  ↓
Test Specification
  └─ Test Case
```

BFC初版は、業務要件からシステム機能候補を洗い出すための上流成果物である。

機能一覧は、BFCで洗い出した機能候補を正式な設計・実装・テスト単位として整理し、正式な機能IDを付与する成果物である。

機能一覧確定後は、正式な機能IDをBFCへ反映する。

機能設計の結果、機能の統合、分割、共通化または実装方式の変更が発生した場合は、機能一覧とBFCを更新し、必要に応じて後続のデータフローおよびTest Specificationへ影響を反映する。

Test SpecificationとTest Caseの具体的なYAML形式は、[`test-case-schema.md`](./test-case-schema.md)に従う。

## 1. 共通ID管理ルール

### 1.1 基本方針

- IDは一意とする
- IDは名称変更時にも原則として維持する
- 廃止したIDを別の対象へ再利用しない
- 表示順を変えるために既存IDを振り直さない
- 欠番を許容する
- AIは未登録の対象へ推測でIDを割り当てない
- IDを変更する場合は、全参照先を同一Pull Requestで変更する

### 1.2 ID体系

| 対象 | ID例 |
|---|---|
| 要件 | `REQ001` |
| ユースケース | `UC001` |
| データフロー | `DF001` |
| アプリ | `UI001` |
| Screen | `UI001-01` |
| インターフェース | `IF001` |
| バッチ | `BT001` |
| レポート | `RP001` |
| 共通 | `CM001` |
| データ移行 | `MG001` |
| 機能単体Test Specification | `FUT-UI001-01-001` |
| 機能間結合Test Specification | `FIT-DF001-001` |
| システムTest Specification | `ST-UC001-001` |
| Test Case | `C001` |
| 実行ケースID | `FUT-UI001-01-001-C001` |

`FUT` / `FIT` / `ST`形式のIDは、要件や機能から直接追跡するTest SpecificationのIDとする。

Test CaseはTest Specification配下の具体的なデータ・入力・期待結果パターンであり、`C001`形式で採番する。

実行結果、証跡、Playwrightテスト名等で一意に識別する場合は、`<test_spec_id>-<case_id>`を使用する。

## 2. ビジネスファンクションチャート（BFC）

### 2.1 目的

BFCは、業務要件を起点として、業務を成立させるために必要な人とシステムの振る舞いを整理し、必要なシステム機能候補を洗い出すための上流成果物とする。

BFCでは、以下を一つの業務の流れとして扱う。

- 誰が行うか
- いつ行うか
- 何を行うか
- その業務に対してシステムが何を担うか

人だけでなく、システムによる処理も業務を構成する主体として扱う。

BFCは、実装資産の一覧や完成済み機能一覧を転記するための表ではない。

### 2.2 BFC初版の位置づけ

BFC初版は、機能一覧より前に作成する。

この段階では、業務要件を満たすために必要な「機能候補」を洗い出すことを目的とする。

原則として、以下を早期に確定しない。

- 共通化するかどうか
- 複数機能を統合するかどうか
- 1機能を複数機能へ分割するかどうか
- Power Apps、Power Automate、Azure Functions等の具体的な実装配置
- 共通UDFや共通メソッドとして切り出すかどうか
- 正式な機能ID

既存システム分析等で実装方式が既に決まっている場合は、実装情報を参考情報として記載してよい。

### 2.3 ユースケースID

BFCで整理した業務上の振る舞いに、`UC`と3桁以上の連番でユースケースIDを付与する。

```text
UC001
UC002
UC003
```

ユースケースは、人の操作だけに限定しない。

業務を成立させるために必要なシステム処理も含め、BFC上で業務要件との対応を明確にする。

### 2.4 BFC初版の必須項目

| 項目 | 内容 |
|---|---|
| 業務分類 | 休暇申請、残業申請、申請管理等の業務グループ |
| ユースケースID | `UC001`形式の一意なID |
| 関連要件ID | 根拠となる`REQ001`等 |
| 主語 | メンバー、管理者、システム、外部システム等 |
| タイミング | 事前、事後、毎週、締め日前、イベント発生時等 |
| 業務要件 | 主語が実施する業務上の振る舞い・目的 |
| 機能候補名 | 業務を実現するために必要と考えるシステム機能候補 |
| 機能候補要件 | 当該機能候補が実現すべき内容 |
| 機能分類候補 | UI、IF、BT、RP等。判断できる場合のみ |
| 実装候補 | Apps、Automate、Functions等。判断済みの場合のみ |
| 正式機能ID | BFC初版では`未採番`可 |

BFC初版では、機能候補ごとに正式機能IDを割り当てる必要はない。

### 2.5 業務要件と機能候補の関係

1つのBusiness Requirement（業務要件）に対して、複数のシステム機能候補を対応付けてよい。

例えば、1つの「申請を登録する」という業務要件を実現するために、以下の複数機能候補が必要となる場合がある。

```text
Business Requirement
「申請を登録する」
  ├─ 申請入力
  ├─ 申請登録処理
  └─ 承認依頼通知
```

この関係は、業務要件とシステム機能候補の`1:N`関係である。

BFCでは、1つの業務要件を無理に1つのシステム機能候補へまとめない。
業務要件を成立させるために必要なシステムの振る舞いを、必要な粒度で複数行に分けて記載してよい。

### 2.6 BFCから機能一覧への移行

上記の「業務要件 1 : N 機能候補」と、BFC機能候補から正式機能への対応関係は別の概念として扱う。

BFCで洗い出した1つの機能候補を、そのまま1つの正式機能として機能一覧へ登録する必要はない。

機能一覧作成時には、設計・実装・テスト可能な責務単位として整理し、必要に応じて以下を行う。

- 統合
- 分割
- 共通化
- 責務の移動
- 機能種別の確定
- 実装方式の確定
- 正式機能IDの採番

BFCは業務上必要な振る舞いを漏れなく洗い出すための成果物、機能一覧はシステムとして正式な機能責務を管理する成果物として区別する。

### 2.7 BFC更新

機能一覧で正式な機能IDを確定した後、BFCの機能候補と正式機能IDを紐付ける。

1つの機能候補が複数の正式機能へ分割されてもよい。

複数の機能候補が1つの正式機能へ統合されてもよい。

共通機能が設計段階で新たに抽出された場合は、関連するユースケースへ正式機能IDを追記する。

### 2.8 機能設計後のフィードバック

各機能の詳細設計や実装検討の結果、以下が発生した場合は機能一覧を更新し、その結果をBFCへフィードバックする。

- 機能統合
- 機能分割
- 共通化
- 責務変更
- 実装方式変更
- 機能廃止
- 新規機能追加

BFC初版の機能候補を、設計変更に合わせて無理に維持する必要はない。

ただし、元の業務要件がどの正式機能によって実現されるかを追跡できる状態は維持する。

## 3. ユースケース間依存関係表

### 3.1 目的

BFCで整理したユースケース間の業務上の依存関係を明確にし、システム設計およびシステムテストの影響分析に利用する。

ユースケースの前後関係は、単なる画面遷移順だけで判断しない。

以下のいずれかに該当する場合に依存関係ありとする。

- 前ユースケースの出力データを利用する
- 前ユースケースの状態変更を前提とする
- 前ユースケースが事前条件となる
- 後続ユースケースの入力またはトリガーとなる

### 3.2 必須項目

| 項目 | 内容 |
|---|---|
| ユースケースID | 対象ユースケース |
| 前提ユースケースID | 実行前に必要なユースケース |
| 後続ユースケースID | 出力を利用するユースケース |
| 依存データ・状態 | 関係を生むデータまたは状態 |
| 影響方向 | 前方、後方、双方向 |

## 4. 機能一覧

### 4.1 目的

機能一覧は、BFCで洗い出した機能候補を、設計・実装・テスト可能な正式なシステム機能単位として整理する成果物とする。

機能一覧を正式な機能IDと責務の管理元とする。

データフロー、Test Specification、変更影響分析等の下流成果物は、機能一覧で確定した正式な機能IDを参照する。

### 4.2 機能ID体系

| 機能種別 | ID例 | 単位 |
|---|---|---|
| アプリ / UI | `UI001` | 1キャンバスアプリ。親管理単位 |
| 画面 | `UI001-01` | `UI001`配下の1 Screenオブジェクト |
| インターフェース | `IF001` | 外部システムとの1送受信機能 |
| バッチ | `BT001` | 定期・一括・非同期で実行する1処理 |
| レポート | `RP001` | 1帳票 |
| 共通 | `CM001` | 1公開UDFまたは1公開メソッド |
| データ移行 | `MG001` | 1移行先 |

画面の子番号は、文字列順でも正しく並ぶように2桁以上でゼロ埋めする。

```text
UI001
├─ UI001-01 申請入力画面
├─ UI001-02 申請履歴画面
└─ UI001-03 申請詳細画面
```

`UI001`はアプリ全体を表す親管理単位であり、画面の機能単体テストは原則として`UI001-01`以下のScreen機能を対象とする。

IFとBTは実装技術ではなく責務で分類する。

- 外部システムとの送受信が主目的：`IF`
- 定期、スケジュール、一括または非同期処理が主目的：`BT`

### 4.3 機能一覧の必須項目

| 項目 | 内容 |
|---|---|
| 機能ID | 本標準に従った一意のID |
| 親機能ID | Screenの場合の親アプリID等 |
| 機能名 | 業務上の名称 |
| 機能種別 | UI、画面、IF、BT、RP、CM、MG |
| 実装資産名 | Screen名、フロー名、Function名等 |
| 主な入力 | 受け取る値・データ・メッセージ |
| 主な出力 | 作成・更新・返却する値・状態 |
| SharePoint | 読み書きするリスト・列 |
| 外部接続先 | API、外部システム等 |
| 呼出し元 | 当該機能を起動する機能 |
| 呼出し先 | 当該機能が起動する機能 |
| 関連ユースケース | BFCで定義したユースケースID |
| 所有者 | 担当チームまたは責任者 |
| 状態 | 計画中、開発中、利用中、廃止等 |

### 4.4 作成・更新ルール

- 機能一覧はBFC初版とユースケース間依存関係表を参照して作成する
- 1つの業務要件に複数のBFC機能候補を対応付けてよい
- BFC機能候補と正式機能は1対1である必要はなく、設計結果に応じて統合・分割・共通化してよい
- すべての正式機能に一意な機能IDを付与する
- 機能一覧で正式IDを確定した後、BFCへ機能IDを反映する
- 機能設計で統合・分割・共通化等が発生した場合は、機能一覧を更新しBFCへ反映する
- データフローおよびTest Specificationは正式機能IDを参照する

## 5. データフロー対応表

### 5.1 目的

正式な機能IDが確定した後、データの生成元、保存先・中継先、利用先を明確にし、機能間結合テストの母数と変更影響分析に利用する。

### 5.2 データフローID

データフローIDは`DF`と3桁以上の連番で構成する。

```text
DF001
DF002
DF003
```

### 5.3 結合テスト経路の定義

機能間結合テストは、データまたはメッセージを受け渡す入力機能、データストア・インターフェース、および出力機能から構成される1つの連携経路を単位とする。

例：

```text
UI001-01 → sp_requests → UI001-02
UI001-01 → sp_requests → RP001
UI001-01 → BT001 → sp_requests → UI001-02
UI001-01 → IF001 → 外部システム
外部システム → IF002 → sp_requests → UI001-02
```

### 5.4 結合テストの母数

結合テスト対象の母数は、DFDまたはデータフロー対応表に定義された、実際に同一データまたはメッセージを受け渡す連携経路の総数とする。

入力機能と出力機能の単純な直積は使用しない。実在しない経路を母数へ含めない。

1つの入力データを複数の機能が利用する場合は、利用先ごとにデータフローを定義する。

### 5.5 必須項目

| 項目 | 内容 |
|---|---|
| データフローID | `DF001`形式の一意なID |
| データ・メッセージ名 | 受け渡す情報 |
| 生成元機能ID | 入力または生成する機能 |
| 中継・保存先 | SharePoint、IF、BT、外部システム等 |
| 利用先機能ID | 表示、帳票、後続処理等 |
| スキーマ定義 | 列、型、必須、コード値等の参照先 |
| 業務キー・相関ID | 同一データを追跡する識別子 |
| トリガー | 手動、登録、スケジュール、API等 |
| 正常時の状態 | 保存・送信・表示結果 |
| 異常時の状態 | エラー、再実行、残存データ等 |
| 関連機能間結合Test Specification | `FIT-DF001-001`形式の`test_spec_id` |

## 6. 要件・BFC・機能・Test Specification対応

### 6.1 要件ID

要件IDは`REQ`と3桁以上の連番で構成する。

```text
REQ001
REQ002
REQ003
```

### 6.2 トレーサビリティの考え方

最終的に、承認済み業務要件から以下を追跡できる状態にする。

```text
REQ
 ↓
BFC / UC
 ↓
正式機能
 ↓
データフロー
 ↓
Test Specification
 └─ Test Case
```

BFC初版では正式機能IDが未採番でもよい。

機能一覧確定後にBFCへ正式機能IDを紐付けることで、要件から正式機能までのトレーサビリティを完成させる。

### 6.3 Test Specificationの追跡粒度

要件、ユースケース、機能、データフローから直接追跡する単位は、原則としてTest Specificationとする。

Test CaseはTest Specificationの配下で、具体的な`test_data × input_data → expected_result`のパターンとして追跡する。

```text
REQ001
  ↓
UC001
  ↓
FUT-UI001-01-001
  ├─ C001
  ├─ C002
  ├─ C003
  └─ C004
```

要件対応表へすべてのCase IDを重複記載することは必須としない。

### 6.4 対応表の例

```yaml
requirements:
  REQ001:
    title: 申請登録
    use_cases:
      - UC001
    features:
      - UI001-01
      - BT001
      - CM001
    sharepoint_lists:
      - sp_requests
    data_flows:
      - DF001
      - DF003
      - DF004
    test_specs:
      - FUT-UI001-01-001
      - FUT-BT001-001
      - FUT-CM001-001
      - FIT-DF001-001
      - FIT-DF003-001
      - FIT-DF004-001
      - ST-UC001-001
```

### 6.5 Test SpecificationからTest Caseへの追跡

Test Specification YAML内で、各Caseを一意に管理する。

```yaml
test_spec_id: FUT-UI001-01-001

cases:
  - case_id: C001
    test_data_refs:
      - TD001
    input_data_refs:
      - IN001
    expected_result:
      result: accepted

  - case_id: C002
    test_data_refs:
      - TD002
    input_data_refs:
      - IN001
    expected_result:
      result: rejected
```

## 7. 変更影響分析

AIは、Git差分および本標準の成果物から、以下を影響範囲候補として抽出する。

### 7.1 業務要件・BFC

- 変更された業務要件
- 変更されたBFCのユースケース
- 変更された主語・タイミング・業務要件
- 追加・削除された機能候補
- BFCと正式機能IDの対応変更

### 7.2 直接影響

- 変更されたScreen
- 変更されたコントロール
- 変更されたPower Fx
- 変更されたUser Defined Function
- 変更されたPower Automate
- 変更されたAzure Functions
- 変更されたSharePointリスト・列
- 変更されたレポート
- 変更された機能一覧の項目
- 変更されたTest Specification
- 変更されたTest Case

### 7.3 呼出し関係

- 変更機能を呼び出す機能
- 変更機能から呼び出す機能
- 共通機能の利用元
- 親機能・子機能

### 7.4 データフロー関係

- 変更機能が生成するデータの利用先
- 変更したSharePointリストを読み書きする全機能
- 変更した列を利用する画面、帳票、IF、BT
- 同一データフロー経路に属する機能
- 関連する機能間結合Test Specification

### 7.5 ユースケース関係

- 変更機能を利用するBFC上のユースケース
- 当該ユースケースの前提ユースケース
- 当該ユースケースの出力を利用する後続ユースケース
- 関連するシステムTest Specification

### 7.6 テストデータ・入力データ・期待結果

以下の変更もテスト影響として扱う。

- `test_data`の追加・削除・状態変更
- `input_data`の同値クラス・境界値変更
- 個別条件・判定式の変更
- MC/DCペアの変更
- `expected_result`の変更
- Case追加・削除
- Test Specificationの対象機能・要件・DF・UC変更

AIは影響候補を抽出するが、影響なしと判断した項目についても理由を記録する。

## 8. 更新ルール

以下の変更時には、対応するトレーサビリティ成果物を同一Pull Request内で更新する。

- 業務要件変更
- BFCのユースケース、業務要件または機能候補変更
- 機能追加・削除・責務変更
- 機能統合・分割・共通化
- 機能IDまたは実装資産名の変更
- SharePointリスト・列変更
- 画面間・機能間のデータフロー変更
- IFまたはBTの入出力変更
- ユースケース依存関係変更
- Test Specification追加・削除・対象変更
- Test Case追加・削除
- `test_data` / `input_data` / `expected_result`変更
- MC/DC対象条件またはカバレッジ変更

特に、機能設計の結果として機能の統合・分割・共通化・実装方式変更が発生した場合は、機能一覧だけを更新して終了せず、BFCの正式機能ID対応も更新する。

対応表が更新されていない変更は、レビュー未完了として扱う。

Test Caseだけの追加・削除で、親Test Specificationが同じ要件・機能・DF・UCを参照し続ける場合、上位トレーサビリティ表の変更は必須としない。ただしTest Specification YAML自体は同一Pull Requestで更新する。

## 9. AIによる作成・参照順序

### 9.1 新規設計・業務要件起点

AIが業務要件から設計・テスト成果物を作成する場合は、原則として以下の順序とする。

```text
業務要件
  ↓
BFC 初版
  ↓
ユースケース間依存関係表
  ↓
機能一覧
  ↓
BFC 更新
  ↓
データフロー対応表
  ↓
Test Specification
  ↓
Test Case
```

AIは、BFC初版の段階で共通化・機能分割・実装配置を必要以上に推測して確定しない。

### 9.2 既存システムの変更影響分析

実装変更から影響分析を行う場合は、変更箇所を起点として以下を逆引きしてよい。

```text
変更された実装
  ↓
機能一覧
  ↓
BFC上の関連ユースケース
  ↓
ユースケース間依存関係
  ↓
関連データフロー
  ↓
Test Specification
  └─ Test Case
```

AIは、途中の成果物が存在しない場合に推測で関係を確定せず、不足成果物として報告する。
