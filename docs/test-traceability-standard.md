# Power Apps テスト・トレーサビリティ標準

作成日：2026-08-06  \n改訂日：2026-08-06（機能一覧、ID体系、成果物間参照を統一）

## 0. 目的

本標準は、要件、ユースケース、機能、データフロー、SharePointスキーマ、テストケースおよび変更差分の関係を、AIと人間が追跡できる状態にするための成果物と管理方法を定める。

以下を必須成果物とし、原則として記載順に作成する。

1. 機能一覧
2. データフロー対応表
3. ビジネスファンクションチャート（ユースケース・機能対応表）
4. ユースケース間依存関係表
5. 要件・機能・テスト対応表

後続成果物は、前段の成果物で採番したIDを参照する。

---

## 1. 共通ID管理ルール

### 1.1 基本方針

- IDは一意とする
- IDは名称変更時にも原則として維持する
- 廃止したIDを別の対象へ再利用しない
- 表示順を変えるために既存IDを振り直さない
- 欠番を許容する
- AIは未登録の対象へ推測でIDを割り当てない
- IDを変更する場合は、全参照先を同一Pull Requestで変更する

### 1.2 ID体系

| 対象 | ID例 |
|---|---|
| 要件 | `REQ001` |
| ユースケース | `UC001` |
| データフロー | `DF001` |
| アプリ | `UI001` |
| Screen | `UI001-01` |
| インターフェース | `IF001` |
| バッチ | `BT001` |
| レポート | `RP001` |
| 共通 | `CM001` |
| データ移行 | `MG001` |

## 2. 機能一覧

### 2.1 目的

機能一覧を、データフロー、ビジネスファンクションチャート、テストケースおよび変更影響分析の起点とする。

画面、フロー、Azure Functions、帳票、移行処理、共通処理等を追加した場合は、他の設計成果物やテストケースを作成する前に機能一覧へ登録する。

### 2.2 機能ID体系

| 機能種別 | ID例 | 単位 |
|---|---|---|
| アプリ / UI | `UI001` | 1キャンバスアプリ。親管理単位 |
| 画面 | `UI001-01` | `UI001`配下の1 Screenオブジェクト |
| インターフェース | `IF001` | 外部システムとの1送受信機能 |
| バッチ | `BT001` | 定期・一括・非同期で実行する1処理 |
| レポート | `RP001` | 1帳票 |
| 共通 | `CM001` | 1公開UDFまたは1公開メソッド |
| データ移行 | `MG001` | 1移行先 |

画面の子番号は、文字列順でも正しく並ぶように2桁以上でゼロ埋めする。

```text
UI001
├─ UI001-01 申請入力画面
├─ UI001-02 申請履歴画面
└─ UI001-03 申請詳細画面
```

`UI001`はアプリ全体を表す親管理単位であり、画面の機能単体テストは原則として`UI001-01`以下のScreen機能を対象とする。

IFとBTは実装技術ではなく責務で分類する。

- 外部システムとの送受信が主目的：`IF`
- 定期、スケジュール、一括または非同期処理が主目的：`BT`

### 2.3 機能一覧の必須項目

| 項目 | 内容 |
|---|---|
| 機能ID | 本標準に従った一意のID |
| 親機能ID | Screenの場合の親アプリID等 |
| 機能名 | 業務上の名称 |
| 機能種別 | UI、画面、IF、BT、RP、CM、MG |
| 実装資産名 | Screen名、フロー名、Function名等 |
| 主な入力 | 受け取る値・データ・メッセージ |
| 主な出力 | 作成・更新・返却する値・状態 |
| SharePoint | 読み書きするリスト・列 |
| 外部接続先 | API、外部システム等 |
| 呼出し元 | 当該機能を起動する機能 |
| 呼出し先 | 当該機能が起動する機能 |
| 関連ユースケース | 使用するユースケースID |
| 所有者 | 担当チームまたは責任者 |
| 状態 | 計画中、開発中、利用中、廃止等 |

## 3. データフロー対応表

### 3.1 目的

データの生成元、保存先・中継先、利用先を明確にし、機能間結合テストの母数と変更影響分析に利用する。

### 3.2 データフローID

データフローIDは`DF`と3桁以上の連番で構成する。

```text
DF001
DF002
DF003
```

### 3.3 結合テスト経路の定義

機能間結合テストは、データまたはメッセージを受け渡す入力機能、データストア・インターフェース、および出力機能から構成される1つの連携経路を単位とする。

例：

```text
UI001-01 → sp_requests → UI001-02
UI001-01 → sp_requests → RP001
UI001-01 → BT001 → sp_requests → UI001-02
UI001-01 → IF001 → 外部システム
外部システム → IF002 → sp_requests → UI001-02
```

### 3.4 結合テストの母数

結合テスト対象の母数は、DFDまたはデータフロー対応表に定義された、実際に同一データまたはメッセージを受け渡す連携経路の総数とする。

入力機能と出力機能の単純な直積は使用しない。実在しない経路を母数へ含めない。

1つの入力データを複数の機能が利用する場合は、利用先ごとにデータフローを定義する。

### 3.5 必須項目

| 項目 | 内容 |
|---|---|
| データフローID | `DF001`形式の一意なID |
| データ・メッセージ名 | 受け渡す情報 |
| 生成元機能ID | 入力または生成する機能 |
| 中継・保存先 | SharePoint、IF、BT、外部システム等 |
| 利用先機能ID | 表示、帳票、後続処理等 |
| スキーマ定義 | 列、型、必須、コード値等の参照先 |
| 業務キー・相関ID | 同一データを追跡する識別子 |
| トリガー | 手動、登録、スケジュール、API等 |
| 正常時の状態 | 保存・送信・表示結果 |
| 異常時の状態 | エラー、再実行、残存データ等 |
| 関連結合テスト | `FIT-DF001-001`形式のテストケースID |

サンプル：

## 4. ビジネスファンクションチャート

### 4.1 目的

各ユースケースが利用する機能を明確にし、変更機能がどの業務シナリオへ影響するかを追跡する。

### 4.2 ユースケースID

ユースケースIDは`UC`と3桁以上の連番で構成する。

```text
UC001
UC002
UC003
```

### 4.3 必須項目

| 項目 | 内容 |
|---|---|
| ユースケースID | `UC001`形式の一意なID |
| ユースケース名 | 利用者が達成する業務目的 |
| アクター | 実行者 |
| 使用機能ID | 機能一覧で定義した機能ID |
| 入力データ | 前提となるデータ |
| 出力データ・状態 | 作成・更新するデータや状態 |
| 関連データフローID | 当該ユースケースが利用するデータフロー |
| 関連システムテスト | `ST-UC001-001`形式のテストケースID |

ビジネスファンクションチャートは、単なる画面一覧ではなく、利用者の業務目的と機能の対応を表す。

サンプル：

- [ビジネスファンクションチャートサンプル](../samples/test-design/business-function-chart-sample.md)

## 5. ユースケース間依存関係表

ユースケースの前後関係は、画面遷移順だけで判断しない。

以下のいずれかに該当する場合に依存関係ありとする。

- 前ユースケースの出力データを利用する
- 前ユースケースの状態変更を前提とする
- 前ユースケースが事前条件となる
- 後続ユースケースの入力またはトリガーとなる

| 項目 | 内容 |
|---|---|
| ユースケースID | 対象ユースケース |
| 前提ユースケースID | 実行前に必要なユースケース |
| 後続ユースケースID | 出力を利用するユースケース |
| 依存データ・状態 | 関係を生むデータまたは状態 |
| 影響方向 | 前方、後方、双方向 |

## 6. 要件・機能・テスト対応表

### 6.1 要件ID

要件IDは`REQ`と3桁以上の連番で構成する。

```text
REQ001
REQ002
REQ003
```

### 6.2 対応表

承認済み要件から、ユースケース、実装機能、SharePoint、データフローおよびテストケースを追跡できる状態にする。

```yaml
requirements:
  REQ001:
    title: 申請登録
    use_cases:
      - UC001
    features:
      - UI001-01
      - BT001
      - CM001
    sharepoint_lists:
      - sp_requests
    data_flows:
      - DF001
      - DF002
    tests:
      - FUT-UI001-01-001
      - FUT-BT001-001
      - FUT-CM001-001
      - FIT-DF001-001
      - FIT-DF002-001
      - ST-UC001-001
```

## 7. 変更影響分析

AIは、Git差分および本標準の対応表から、以下を影響範囲候補として抽出する。

### 7.1 直接影響

- 変更されたScreen
- 変更されたコントロール
- 変更されたPower Fx
- 変更されたUser Defined Function
- 変更されたPower Automate
- 変更されたAzure Functions
- 変更されたSharePointリスト・列
- 変更されたレポート
- 変更された機能一覧の項目

### 7.2 呼出し関係

- 変更機能を呼び出す機能
- 変更機能から呼び出す機能
- 共通機能の利用元
- 親機能・子機能

### 7.3 データフロー関係

- 変更機能が生成するデータの利用先
- 変更したSharePointリストを読み書きする全機能
- 変更した列を利用する画面、帳票、IF、BT
- 同一データフロー経路に属する機能
- 関連する機能間結合テスト

### 7.4 ユースケース関係

- 変更機能を利用するユースケース
- 当該ユースケースの前提ユースケース
- 当該ユースケースの出力を利用する後続ユースケース
- 関連するシステムテスト

AIは影響候補を抽出するが、影響なしと判断した項目についても理由を記録する。

## 8. 更新ルール

以下の変更時には、対応するトレーサビリティ成果物を同一Pull Request内で更新する。

- 機能追加・削除・責務変更
- 機能IDまたは実装資産名の変更
- SharePointリスト・列変更
- 画面間・機能間のデータフロー変更
- IFまたはBTの入出力変更
- ユースケース変更
- テストケース追加・削除・期待結果変更

対応表が更新されていない変更は、レビュー未完了として扱う。
