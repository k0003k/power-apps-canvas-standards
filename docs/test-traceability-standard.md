# Power Apps テスト・トレーサビリティ標準

作成日：2026-08-06

## 0. 目的

本標準は、要件、ユースケース、機能、データフロー、SharePointスキーマ、テストケースおよび変更差分の関係を、AIと人間が追跡できる状態にするための成果物と管理方法を定める。

以下を必須成果物とする。

1. 機能一覧
2. データフロー対応表
3. ビジネスファンクションチャート（ユースケース・機能対応表）
4. ユースケース間依存関係表
5. 要件・機能・テスト対応表

---

## 1. 機能一覧

各機能に一意な機能IDを付与する。

| 機能種別 | ID例 |
|---|---|
| 画面 | `SCR-REQUEST-ENTRY` |
| レポート | `RPT-REQUEST-LIST` |
| Power Automate | `FLOW-SUBMIT-REQUEST` |
| Azure Functions関数 | `FUNC-SEND-REQUEST` |
| データ移行 | `MIG-SP-REQUESTS` |
| 共通メソッド | `COMMON-VALIDATE-REQUEST` |

機能一覧には、少なくとも以下を記録する。

- 機能ID
- 機能名
- 機能種別
- 実装資産名
- 入力
- 出力
- 読み書きするSharePointリスト・列
- 呼出し元
- 呼出し先
- 関連ユースケース
- 所有者

## 2. データフロー対応表

### 2.1 目的

データの生成元、保存先・中継先、利用先を明確にし、機能間結合テストの母数と変更影響分析に利用する。

### 2.2 結合テスト経路の定義

機能間結合テストは、データまたはメッセージを受け渡す入力機能、データストア・インターフェース、および出力機能から構成される1つの連携経路を単位とする。

例：

```text
入力画面 → SharePointリスト → 一覧画面
入力画面 → SharePointリスト → 帳票
画面 → Power Automate → SharePointリスト → 一覧画面
画面 → Azure Functions関数 → 外部システム
外部システム → Azure Functions関数 → SharePointリスト → 一覧画面
```

### 2.3 結合テストの母数

結合テスト対象の母数は、DFDまたはデータフロー対応表に定義された、実際に同一データまたはメッセージを受け渡す連携経路の総数とする。

入力機能と出力機能の単純な直積は使用しない。実在しない経路を母数へ含めない。

1つの入力データを複数の機能が利用する場合は、利用先ごとに経路を定義する。

```text
入力画面 → SharePoint → 一覧画面
入力画面 → SharePoint → 帳票
入力画面 → SharePoint → バッチ
```

### 2.4 必須項目

| 項目 | 内容 |
|---|---|
| データフローID | 一意な識別子 |
| データ・メッセージ名 | 受け渡す情報 |
| 生成元機能 | 入力または生成する機能 |
| 中継・保存先 | SharePoint、フロー、Function、外部IF等 |
| 利用先機能 | 表示、帳票、後続処理等 |
| スキーマ定義 | 列、型、必須、コード値等の参照先 |
| トリガー | 手動、登録、スケジュール、API等 |
| 正常時の状態 | 保存・送信・表示結果 |
| 異常時の状態 | エラー、再実行、残存データ等 |
| 関連結合テスト | テストケースID |

## 3. ビジネスファンクションチャート

### 3.1 目的

各ユースケースが利用する機能を明確にし、変更機能がどの業務シナリオへ影響するかを追跡する。

### 3.2 必須項目

| 項目 | 内容 |
|---|---|
| ユースケースID | 一意な識別子 |
| ユースケース名 | 利用者が達成する業務目的 |
| アクター | 実行者 |
| 使用機能 | 画面、フロー、Function、帳票、共通機能等 |
| 入力データ | 前提となるデータ |
| 出力データ・状態 | 作成・更新するデータや状態 |
| 関連システムテスト | テストケースID |

ビジネスファンクションチャートは、単なる画面一覧ではなく、利用者の業務目的と機能の対応を表す。

---

## 4. ユースケース間依存関係表

ユースケースの前後関係は、画面遷移順だけで判断しない。

以下のいずれかに該当する場合に依存関係ありとする。

- 前ユースケースの出力データを利用する
- 前ユースケースの状態変更を前提とする
- 前ユースケースが事前条件となる
- 後続ユースケースの入力またはトリガーとなる

記録項目：

| 項目 | 内容 |
|---|---|
| ユースケースID | 対象ユースケース |
| 前提ユースケース | 実行前に必要なユースケース |
| 後続ユースケース | 出力を利用するユースケース |
| 依存データ・状態 | 関係を生むデータまたは状態 |
| 影響方向 | 前方、後方、双方向 |

## 5. 要件・機能・テスト対応表

承認済み要件から実装機能とテストケースを追跡できる状態にする。

```yaml
requirements:
  REQ-001:
    title: 申請登録
    use_cases:
      - UC-REQUEST-SUBMIT
    features:
      - SCR-REQUEST-ENTRY
      - FLOW-SUBMIT-REQUEST
      - COMMON-VALIDATE-REQUEST
    sharepoint_lists:
      - sp_requests
    data_flows:
      - DF-REQUEST-ENTRY-TO-LIST
      - DF-REQUEST-LIST-TO-HISTORY
    tests:
      - FUT-SCR-REQUEST-001
      - FIT-REQUEST-ENTRY-HISTORY-001
      - ST-REQUEST-SUBMIT-001
```

## 6. 変更影響分析

AIは、Git差分および本標準の対応表から、以下を影響範囲候補として抽出する。

### 6.1 直接影響

- 変更されたScreen
- 変更されたコントロール
- 変更されたPower Fx
- 変更されたUser Defined Function
- 変更されたPower Automate
- 変更されたAzure Functions関数
- 変更されたSharePointリスト・列
- 変更されたレポート

### 6.2 呼出し関係

- 変更機能を呼び出す機能
- 変更機能から呼び出す機能
- 共通メソッドの利用元

### 6.3 データフロー関係

- 変更機能が生成するデータの利用先
- 変更したSharePointリストを読み書きする全機能
- 変更した列を利用する画面、帳票、IF、バッチ
- 同一データフロー経路に属する機能
- 関連する機能間結合テスト

### 6.4 ユースケース関係

- 変更機能を利用するユースケース
- 当該ユースケースの前提ユースケース
- 当該ユースケースの出力を利用する後続ユースケース
- 関連するシステムテスト

AIは影響候補を抽出するが、影響なしと判断した項目についても理由を記録する。

---

## 7. 更新ルール

以下の変更時には、対応するトレーサビリティ成果物を同一Pull Request内で更新する。

- 機能追加・削除・責務変更
- SharePointリスト・列変更
- 画面間・機能間のデータフロー変更
- フローまたはFunctionの入出力変更
- ユースケース変更
- テストケース追加・削除・期待結果変更

対応表が更新されていない変更は、レビュー未完了として扱う。
