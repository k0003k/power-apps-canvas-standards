# Power Apps AI自動テスト標準

作成日：2026-08-06

## 0. 目的・適用範囲

本標準は、Power Apps キャンバスアプリ、SharePoint、Power Automate、Azure Functions、レポート、データ移行アプリおよび共通機能について、AIがテスト仕様書を作成し、自動テストを継続実行するための標準を定める。

本標準の目的は以下とする。

- 仕様とコードからAIがテストケースを生成できること
- 1機能の責務を、実際のSharePoint処理を含めて検証できること
- 機能間の接続先、スキーマ、コード値、データフローの齟齬を検出できること
- ユースケースに沿って業務目的が達成できることを確認できること
- 仕様変更時に、呼出し関係、データフロー、ユースケースから影響テストを選択できること

非機能テストは本版の対象外とし、別標準で定義する。大量データを用いた性能確認も非機能テストとして扱う。

参考：

- [Power Platform Playwright samples overview](https://learn.microsoft.com/en-us/power-platform/developer/playwright-samples/overview)
- [Test Canvas Apps](https://learn.microsoft.com/en-us/power-platform/developer/playwright-samples/canvas-application)
- [Playwright MCP server for Power Platform testing](https://learn.microsoft.com/en-us/power-platform/developer/playwright-samples/ai-mcp)
- [Authentication guide](https://learn.microsoft.com/en-us/power-platform/developer/playwright-samples/authentication-guide)

## 1. テスト分類と実行方式

### 1.1 3つのテスト分類

| テスト分類 | 保証する対象 |
|---|---|
| 機能単体テスト | 1機能が、コード上の分岐、異常系、データ処理を含めて責務を完結できること |
| 機能間結合テスト | データまたはメッセージを受け渡す機能間の連携経路が、同じ接続先・スキーマ・コード値を使用し、データ整合性を維持できること |
| システムテスト | 利用者がユースケースに沿って一連の業務目的を達成できること |

本標準における機能単体テストは、一般的なプログラミング言語における関数・クラス単位のユニットテストだけを意味しない。

プロジェクトで定義した1機能を対象とする「機能単体テスト」を、単体テストと呼ぶ。

### 1.2 テスト分類は工程ではない

機能単体、機能間結合、システムは、順番に実施する開発工程を意味しない。各テストケースが保証する対象と目的を示す分類である。

AIによる自動テストでは、変更内容、データフロー、ユースケースへの影響に応じて、複数のテスト分類を1回のテスト実行に組み合わせてよい。

### 1.3 実行プロファイル

| 実行プロファイル | 目的 |
|---|---|
| スモークテスト | PRまたはデプロイごとに、短時間で主要機能の破損を検出する |
| 変更影響テスト | Git差分、呼出し関係、データフロー、ユースケースから選択したテストを実行する |
| フルリグレッションテスト | 夜間、定期実行またはリリース前に、全体を確認する |

## 2. 環境標準

### 2.1 環境

以下の環境を用意する。

- 開発環境
- 試験環境
- 本番環境

開発環境および試験環境には、本番業務データを投入しない。

自動更新を伴うテストは、原則として開発環境または試験環境で実行する。

### 2.2 本番環境でのテスト

本番環境では、原則としてテストを実施しない。

理由は以下とする。

- 業務データへ影響する
- テストデータの削除が必要になる
- フローまたは外部インターフェースが実行される
- 通知、帳票、メール等が実際に送信される可能性がある
- 証跡に本番データが含まれる可能性がある

例外的に本番環境でテストする場合は、以下を必須とする。

- 実施責任者の承認
- 対象機能と実施時間帯の明示
- 可能な限り参照のみのテスト
- テストデータの一意な識別
- 外部送信・通知の抑止
- 作成・更新したデータの一覧
- 後処理手順と後処理責任者
- ロールバックまたは復旧手順
- 証跡のアクセス制限
- 本番データを含む証跡のマスキング
- 保存期間と削除期限

## 3. 1機能の定義

| 機能種別 | 1機能の単位 | 補足 |
|---|---|---|
| レポート | 1帳票 | 画面一覧、Excel、PDF、Power BI等の1出力単位 |
| インターフェース / バッチ | 1 Azure Functions関数または1親Power Automateフロー | Azure Functionsは原則として1トリガーまたは1エンドポイント。子フローは親フローに含める |
| 画面 | 1 `Screen` オブジェクト | `scr_`で始まる1画面を1機能とする |
| データ移行アプリ | 1移行先 | 原則として1つのSharePointリストまたはドキュメントライブラリを1機能とする |
| 共通 | 1公開User Defined Functionまたは1公開メソッド | 非公開補助メソッドは、原則として呼出し元の公開メソッドを通じて確認する |

複数の親フローから再利用され、独立した業務ルールと明確な入出力仕様を持つ子フローは、共通機能として独立テストを作成してよい。

## 4. 機能単体テスト

### 4.1 基本方針

機能単体テストは、1機能がその責務を完結できることを確認する。

画面機能がSharePointへの登録、更新または削除を責務として持つ場合、実際の開発・試験環境用SharePointリストへの処理結果と保存値の妥当性までをテスト対象に含める。

外部機能を呼び出す場合も、1機能として完結する処理範囲に実接続が必要であれば、テスト環境の実接続先を用いて確認する。

### 4.2 期待する網羅

対象機能に適用可能な以下の観点を確認する。

- 正常系
- 異常系
- 未入力、空白、Null相当
- 境界値
- 0件、1件、複数件
- 条件分岐
- 状態遷移
- SharePoint登録・更新・削除
- 外部機能呼出し
- エラー処理
- 再実行
- 二重操作
- 権限不足
- タイムアウト
- リトライ
- 部分失敗

適用しない観点は無理にテストケースを作成せず、`N/A`と理由を記録する。

AIは、対象コードまたは処理経路とテストケースの対応を示す。

### 4.3 Azure Functionsのコード網羅

利用言語のテストフレームワークを使用し、可能な範囲で以下を取得・確認する。

- ステートメントカバレッジ
- ブランチカバレッジ
- 関数・メソッドカバレッジ
- 例外処理
- 入力値の同値分割
- 境界値
- 外部接続の成功・失敗
- タイムアウト
- リトライ
- 冪等性

数値目標を設定していない場合でも、未テストの分岐と理由をAIが説明できることを必須とする。

### 4.4 キャンバスアプリ、Power Fx、User Defined Functionのコード網羅

一般的なソースコードと同等の実行カバレッジを常に取得できるとは限らないため、以下に基づく構文・分岐・状態・副作用の網羅を使用する。

- `If`、`Switch`等の分岐
- 条件式の真・偽
- 正常・異常
- 境界値
- 状態遷移
- 表示・非表示
- 活性・非活性
- SharePointへの副作用
- 画面遷移
- 外部機能呼出し
- エラー処理

実行カバレッジではない場合は、テスト結果にその旨を明記する。

### 4.5 Power Automate、レポート、データ移行等の網羅

以下を基準とする。

- 処理経路
- 条件分岐
- データパターン
- 状態
- 0件、1件、複数件
- 正常・異常
- 再実行
- 部分失敗
- 外部機能との入出力

### 4.6 画面機能の必須観点

- 初期表示
- `OnVisible`実行後の状態
- 入力項目の初期値
- 必須、形式、桁数、範囲等の入力検証
- 表示・非表示
- 活性・非活性
- 画面内の計算・状態変更
- SharePointへの登録、更新、削除
- 保存された列値と件数
- Lookup、Choice、Person列
- 保存成功・失敗後の画面状態
- 二重押下、連続操作、再実行
- 画面遷移と引数
- 共通メソッド、フロー、Functionへの入力値

### 4.7 レポートの必須観点

- 抽出条件
- 検索期間
- 0件、1件、複数件
- 並び順
- グルーピング
- 集計値
- 小計・合計
- 丸め方法
- 日付・数値の表示形式
- 権限による表示範囲
- Excel、PDF等への出力結果
- 元データ件数との照合
- 金額、数量等の合計照合

### 4.8 インターフェース / バッチの必須観点

- トリガー条件
- 入力パラメーター
- 正常処理
- 条件分岐
- 0件、1件、複数件
- エラー処理
- タイムアウト
- リトライ
- 再実行
- 冪等性
- 部分失敗
- 子フローへの入出力
- 実行結果・ログ
- 送受信スキーマ
- 接続元・接続先間のコード値
- 日時、文字コード、Nullの扱い

**冪等性（べきとうせい）**：同じ処理を同じ条件で複数回実行しても、意図しない重複登録や二重処理が発生せず、業務上の結果が不整合にならない性質をいう。処理のたびに結果を追加することが正しい場合は、その期待動作を仕様へ明記する。

### 4.9 データ移行アプリの必須観点

- 移行元件数
- 移行対象件数
- 移行成功件数
- 移行失敗件数
- 除外件数
- 列マッピング
- コード変換
- 既定値
- Null・空白の扱い
- 日時・タイムゾーン
- Lookup、Choice、Person列の変換
- 不正データの隔離
- 重複データ
- 再実行時の動作
- 移行前後の件数照合
- 金額、数量等の合計照合
- エラー内容と再処理可否

複数の移行先間の関連性は、機能間結合テストで確認する。

### 4.10 共通機能の必須観点

- 通常値
- 最小値・最大値
- 境界値の直前・直後
- 空白・Null相当
- 不正な型または形式
- 想定外の列挙値
- 例外またはエラー
- 同じ入力に対する再実行

副作用を持たない処理として実装できる場合は、可能な限り純粋関数として設計する。

## 5. 機能間結合テスト

### 5.1 基本方針

機能間結合テストは、データまたはメッセージを受け渡す入力機能、データストア・インターフェース、および出力機能から構成される1つの連携経路を対象とする。

例：

```text
入力画面 → SharePointリスト → 一覧画面
入力画面 → SharePointリスト → 帳票
画面 → Power Automate → SharePointリスト → 一覧画面
画面 → Azure Functions関数 → 外部システム
```

結合テスト対象の母数は、DFDまたはデータフロー対応表に定義された実在する連携経路の総数とする。

詳細は [`test-traceability-standard.md`](./test-traceability-standard.md) を参照する。

### 5.2 主な検出対象

- 開発者ごとに異なるSharePointリストへ接続している
- 開発用の代替リストが正式接続先として残っている
- 実リストとスキーマ定義書が一致しない
- 入力機能と出力機能で使用列が異なる
- 列内部名、列型、必須設定が異なる
- Choice値、コード値、Nullの扱いが異なる
- 日時・タイムゾーンの扱いが異なる
- Lookup、Person列の保存形式と利用方法が異なる
- IFの接続元と接続先でメッセージスキーマが異なる

### 5.3 必須確認事項

- 正式な接続先を使用していること
- 入力機能で作成したデータを出力機能が利用できること
- 入力から出力まで同一の業務キーを追跡できること
- スキーマ定義と実データが一致すること
- 保存値、表示値、送受信値が一致すること
- 不要なデータ変換や欠損がないこと
- 更新件数が期待値と一致すること
- 関連リスト間のキーが一致すること
- エラー時に不完全データが残らないこと
- 再実行時に意図しない重複が発生しないこと

UI上の成功表示だけで合格とせず、SharePoint、フロー、Function、外部IF等の実結果を確認する。

## 6. システムテスト

### 6.1 基本方針

システムテストは、利用者の業務目的を起点としたユースケース単位で作成する。

以下を一連で確認する。

1. ユーザー、権限、データの準備
2. アプリへのサインイン
3. 画面操作
4. 入力、確認、登録
5. Power AutomateまたはAzure Functionsの実行
6. SharePointデータの更新
7. 後続画面、履歴、レポートへの反映
8. エラー発生時の利用者への案内
9. テストデータの後処理

シナリオは、可能な限りGiven / When / Then形式で記述する。

### 6.2 必須トレーサビリティ

以下を必須成果物とする。

- ビジネスファンクションチャート
- ユースケース・機能対応表
- ユースケース間依存関係表

変更機能を利用するユースケースだけでなく、当該ユースケースとデータまたは状態の依存関係を持つ前提・後続ユースケースも影響範囲候補へ含める。

## 7. 期待結果の情報源

AIは、期待結果を以下の優先順位で決定する。

1. 承認済み業務要件・ユースケース
2. 承認済み基本設計・詳細設計
3. 承認済み業務ルール・データ定義
4. 承認済みテスト仕様
5. 実装コード

実装コードと上位仕様が異なる場合は、実装コードを期待結果の根拠とせず、仕様不一致として報告する。

情報源が不足して期待結果を確定できない場合は、推測で確定せず、確認事項として報告する。

## 8. AIによるテスト作成と変更統制

### 8.1 テストケース

AIが作成するテストケースは [`test-case-schema.md`](./test-case-schema.md) に従う。

AIは、使用したテスト設計技法、対象コード・分岐・データフロー、適用しない観点と理由を記録する。

### 8.2 AIが行ってはならないこと

- 仕様にない期待結果を確定する
- テストを通すために業務仕様を変更する
- テストを通すためにエラー処理を削除する
- 失敗したテストを理由なく無効化する
- 固定待機時間を増やすだけで不安定なテストを隠す
- 本番環境へ無承認でテストデータを作成する
- 本番データを更新・削除する
- 機密情報をテストコードへ記載する
- 失敗結果を成功として扱う

### 8.3 AIによる変更統制

AIがテスト対象コードとテストコードを同時に変更した場合、以下をPull Requestへ明記する。

- 実装変更
- テスト変更
- 期待結果の変更
- 期待結果変更の根拠となる要件・仕様
- AIが置いた前提・推測

AI自身が生成・変更したテストを、AI自身の判定だけで承認済みとして扱わない。

期待結果を変更する場合は、関連要件、仕様、変更理由を必ず記録する。

PoCおよび原因調査で必要な場合は、以下も保存する。

- 使用したAIモデル
- AI指示ファイルのバージョン
- 入力した仕様のバージョン
- テスト生成時のGitコミットID
- 実行したタスクまたはプロンプト

## 9. 変更影響分析とリグレッションテスト

### 9.1 影響範囲

AIは以下の4方向から影響候補を抽出する。

1. 直接変更された機能・コード・SharePoint列
2. 変更機能の呼出し元・呼出し先
3. 同一データフロー経路の入力機能・出力機能
4. 変更機能を利用するユースケースと、データ・状態依存を持つ前提・後続ユースケース

詳細は [`test-traceability-standard.md`](./test-traceability-standard.md) を参照する。

### 9.2 リグレッションテスト

#### スモークテスト

- アプリ起動
- サインイン
- 主要画面表示
- 主要業務の正常系
- 主要なSharePoint登録
- 重大な権限制御

#### 変更影響テスト

- 変更機能の機能単体テスト
- 影響するデータフロー経路の機能間結合テスト
- 影響するユースケースのシステムテスト
- 前提・後続ユースケースのうち、データまたは状態依存を持つシナリオ

#### フルリグレッションテスト

- 全機能単体テスト
- 全機能間結合テスト
- 主要または全システムテスト
- 必要な手動確認

AIが選択したテストだけに依存せず、重要シナリオは変更内容に関係なくスモークテストとして実行する。

## 10. 不安定なテスト

同一コードに対して成功・失敗が不規則に変化するテストを、不安定テストとして管理する。

記録項目：

- テストケースID
- 発生頻度
- 所有者
- 原因
- 暫定対応
- 恒久対応期限

単にリトライして成功したことを理由に、初回失敗を無視しない。

テストを一時的に無効化する場合は、理由、所有者、有効期限を記録する。

## 11. SharePointテストデータと環境同等性

### 11.1 スキーマ確認

テスト実行前に、対象SharePointリストのスキーマが期待する定義と一致することを確認する。

確認対象：

- リスト内部名
- 列内部名
- 列型
- 必須設定
- Choice値
- Lookup先
- Person列の複数選択設定
- 添付ファイル設定
- バージョン管理
- アイテム単位権限
- インデックス

### 11.2 テストデータ識別

テスト実行単位で一意な識別子を付与する。

```text
test_run_id = 20260806-123000-abc123
test_case_id = FUT-SCR-REQUEST-001
```

### 11.3 事前準備と後処理

- 各テストは必要データを自ら準備する
- 他のテストケースが作成したデータへ依存しない
- 成功・失敗にかかわらず後処理を実行する
- 削除条件は `test_run_id` 等で限定する
- 他テストまたは手動作成データを削除しない

### 11.4 並列実行

- テストごとに一意な業務キーを使用する
- 同じレコードを複数テストで更新しない
- 共通マスタを変更しない
- 順序依存のテストを作らない

## 12. UI自動テスト標準

### 12.1 セレクター優先順位

1. Power Platform Playwright ToolkitのPage Objectまたはヘルパー
2. `data-control-name`
3. AccessibleLabel、role、ARIA属性
4. 安定したその他の属性
5. 表示文言
6. DOM階層、CSSクラス、XPath

DOM階層、CSSクラス、XPathへの依存は原則禁止する。

AccessibleLabelは利用者向けの意味を優先し、テストを安定させるためだけに固定しない。

### 12.2 Page Object Model

画面ごとにPage Objectを作成し、以下を定義する。

- 画面固有セレクター
- 画面読込待機
- 入力操作
- ボタン操作
- 表示値取得
- エラー取得
- 画面固有の業務操作

テストシナリオへ複雑なセレクターを直接記述しない。

### 12.3 待機処理

`waitForTimeout()` 等の固定待機は原則として使用しない。

以下を待機条件とする。

- 対象コントロールの表示
- 処理中表示の非表示
- 画面状態の変更
- SharePointレコードの作成・更新
- フローまたはFunctionの完了状態
- エラー表示

固定待機が必要な場合は、理由と根拠を記録する。

### 12.4 テストの独立性

各テストは単独・順不同で実行可能とする。

認証情報の再利用は許容するが、業務データと画面状態はテストごとに初期化する。

### 12.5 認証状態と秘密情報

以下をGitへ保存しない。

- ユーザー名、パスワード
- Client Secret
- 接続文字列
- アクセストークン
- PlaywrightのstorageStateファイル
- 認証済みブラウザーセッション
- 証明書ファイル、証明書パスワード
- 個人情報、本番データ

環境変数、GitHub Secrets、Azure Key Vault等で管理する。

テストアカウントは役割別に分ける。

```text
test_general_user
test_readonly_user
test_approver
test_unauthorized_user
```

## 13. テスト証跡と結果

自動テストでは、必要に応じて以下を保存する。

- 実行日時
- 実行環境
- アプリバージョンまたはGitコミットID
- テストケースID
- 成否
- 実行時間
- エラーメッセージ
- スクリーンショット
- Playwrightトレース
- 動画
- SharePoint検証結果
- Power AutomateまたはAzure Functionsの実行ID
- テストデータ識別子

失敗原因は以下へ分類する。

- 仕様不一致
- 実装不具合
- テストコード不具合
- テストデータ不備
- 環境不備
- 権限不備
- 一時的な通信・サービス障害
- 判定不能

判定できない場合は推測を事実として記載しない。

開発・試験環境には本番データを投入しないため、通常の証跡へ本番データは含まれない前提とする。

例外的に本番環境でテストした場合は、証跡のアクセス制限、マスキング、保存期間、削除期限を設定する。

## 14. テスト実施タイミング

### 14.1 コード生成・Pull Request時

1回の実行で以下を組み合わせる。

- 変更機能の機能単体テスト
- 影響するデータフロー経路の機能間結合テスト
- 主要ユースケースのスモークテスト

### 14.2 試験環境デプロイ後

- 変更機能の機能単体テスト
- 影響する全機能間結合テスト
- 影響するシステムテスト
- 常時実行する主要業務シナリオ

### 14.3 夜間・定期実行

- 全機能単体テスト
- 全機能間結合テスト
- 主要システムテスト

### 14.4 リリース前

- 全機能単体テスト
- 全機能間結合テスト
- 全システムテスト
- 手動確認対象

---

## 15. 完了条件

- テスト仕様書が作成されている
- 対象要件、機能、データフロー、ユースケースとの対応が記録されている
- 正常系、異常系、境界値が含まれている
- 対象コード・処理経路とテストケースの対応が説明されている
- 自動化対象と判定したテストが自動化されている
- 自動化しないテストの理由、実施時期、責任者が記録されている
- SharePoint上のデータ結果が確認されている
- すべての必須テストが成功している
- 未解決の失敗・保留事項が記録されている
- テスト証跡が保存されている
- テストデータが後処理されている
- 変更時は必要なリグレッションテストが実行されている

---

## 16. 自動化対象の判断基準

以下を考慮して自動化対象を決定する。

- 実行頻度
- 業務影響
- リグレッションの重要性
- 自動化の安定性
- テストデータ準備の難易度
- 実装・保守コスト
- 人間による目視判断の必要性
