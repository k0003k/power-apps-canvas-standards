作成日：2026-08-06

## 0. 目的・適用範囲

本標準は、Power Apps キャンバスアプリ、SharePoint、Power Automate、Azure Functions、レポート、データ移行アプリおよび共通機能について、AIがTest SpecificationとTest Caseを作成し、自動テストを継続実行するための標準を定める。

本標準の目的は以下とする。

- 仕様とコードからAIがTest Specificationと具体的なTest Caseを生成できること
- 1機能の責務を、実際のSharePoint処理を含めて検証できること
- 機能間の接続先、スキーマ、コード値、データフローの齟齬を検出できること
- ユースケースに沿って業務目的が達成できることを確認できること
- 仕様変更時に、呼出し関係、データフロー、ユースケースから影響テストを選択できること

非機能テストは本版の対象外とし、別標準で定義する。大量データを用いた性能確認も非機能テストとして扱う。

参考：

- [Power Platform Playwright samples overview](https://learn.microsoft.com/en-us/power-platform/developer/playwright-samples/overview)
- [Test Canvas Apps](https://learn.microsoft.com/en-us/power-platform/developer/playwright-samples/canvas-application)
- [Playwright MCP server for Power Platform testing](https://learn.microsoft.com/en-us/power-platform/developer/playwright-samples/ai-mcp)
- [Authentication guide](https://learn.microsoft.com/en-us/power-platform/developer/playwright-samples/authentication-guide)

## 1. テスト分類と実行方式

### 1.1 3つのテスト分類

| テスト分類 | 保証する対象 |
|---|---|
| 機能単体テスト | 1機能が、コード上の分岐、異常系、データ処理を含めて責務を完結できること |
| 機能間結合テスト | データまたはメッセージを受け渡す機能間の連携経路が、同じ接続先・スキーマ・コード値を使用し、データ整合性を維持できること |
| システムテスト | 利用者がユースケースに沿って一連の業務目的を達成できること |

本標準における機能単体テストは、一般的なプログラミング言語における関数・クラス単位のユニットテストだけを意味しない。

プロジェクトで定義した1機能を対象とする「機能単体テスト」を、単体テストと呼ぶ。

### 1.2 テスト分類は工程ではない

機能単体、機能間結合、システムは、順番に実施する開発工程を意味しない。各テストケースが保証する対象と目的を示す分類である。

AIによる自動テストでは、変更内容、データフロー、ユースケースへの影響に応じて、複数のテスト分類を1回のテスト実行に組み合わせてよい。

### 1.3 実行プロファイル

| 実行プロファイル | 目的 |
|---|---|
| スモークテスト | PRまたはデプロイごとに、短時間で主要機能の破損を検出する |
| 変更影響テスト | Git差分、呼出し関係、データフロー、ユースケースから選択したテストを実行する |
| フルリグレッションテスト | 夜間、定期実行またはリリース前に、全体を確認する |

## 2. 環境標準

### 2.1 環境

以下の環境を用意する。

- 開発環境
- 試験環境
- 本番環境

開発環境および試験環境には、本番業務データを投入しない。

自動更新を伴うテストは、原則として開発環境または試験環境で実行する。

### 2.2 本番環境でのテスト

本番環境では、原則としてテストを実施しない。

理由は以下とする。

- 業務データへ影響する
- テストデータの削除が必要になる
- フローまたは外部インターフェースが実行される
- 通知、帳票、メール等が実際に送信される可能性がある
- 証跡に本番データが含まれる可能性がある

例外的に本番環境でテストする場合は、以下を必須とする。

- 実施責任者の承認
- 対象機能と実施時間帯の明示
- 可能な限り参照のみのテスト
- テストデータの一意な識別
- 外部送信・通知の抑止
- 作成・更新したデータの一覧
- 後処理手順と後処理責任者
- ロールバックまたは復旧手順
- 証跡のアクセス制限
- 本番データを含む証跡のマスキング
- 保存期間と削除期限

## 3. 機能一覧と1機能の定義

### 3.1 機能一覧を先に作成する

テスト仕様書を作成する前に、[`test-traceability-standard.md`](./test-traceability-standard.md)に従って機能一覧を作成する。

機能単体テスト、機能間結合テスト、システムテストは、機能一覧で採番した機能IDを参照する。

実装資産が機能一覧に存在しない場合は、未登録機能として扱い、推測で既存IDへ割り当てない。

### 3.2 1機能の定義

| 機能種別 | ID例 | 1機能の単位 | 補足 |
|---|---|---|---|
| アプリ / UI | `UI001` | 1キャンバスアプリ | 親管理単位。原則として機能単体テスト対象ではなく、配下Screenを対象とする |
| 画面 | `UI001-01` | 1 `Screen` オブジェクト | `scr_`で始まる1画面を1機能とする |
| インターフェース | `IF001` | 外部システムとの1送受信機能 | 実装技術は問わない。1方向の送信・受信を別機能とするかは入出力仕様と責務で判断する |
| バッチ | `BT001` | 定期・一括・非同期で実行する1処理 | 実装技術は問わない。1つの業務処理単位を1機能とする |
| レポート | `RP001` | 1帳票 | 画面一覧、Excel、PDF、Power BI等の1出力単位 |
| データ移行アプリ | `MG001` | 1移行先 | 原則として1つのSharePointリストまたはドキュメントライブラリを1機能とする |
| 共通 | `CM001` | 1公開User Defined Functionまたは1公開メソッド | 非公開補助メソッドは、原則として呼出し元の公開メソッドを通じて確認する |

### 3.3 IFとBTの分類

IFとBTは、Azure Functions、Power Automate等の実装技術ではなく、機能の責務で分類する。

- 外部システムとの送受信が主目的である場合：インターフェース（`IF`）
- 定期、スケジュール、一括、非同期処理が主目的である場合：バッチ（`BT`）

例：

| 実装 | 主な責務 | 分類 |
|---|---|---|
| Azure FunctionsのHTTP Triggerで外部APIへ申請を送信する | 外部送信 | `IF` |
| Azure FunctionsのTimer Triggerで夜間集計する | 定期バッチ | `BT` |
| Power AutomateのHTTP要求で外部結果を受信する | 外部受信 | `IF` |
| Power AutomateのRecurrenceで滞留データを処理する | 定期バッチ | `BT` |

### 3.4 子フロー・内部メソッド

子フローは、原則として親機能の実装詳細として扱い、親機能の機能単体テストに含める。

ただし、複数の親機能から再利用され、独立した業務ルールと明確な入出力仕様を持つ場合は、共通機能（`CM`）として独立したテスト仕様を作成してよい。

## 4. テスト設計共通ルール

### 4.1 Test SpecificationとTest Case

本標準では、テストを以下の二階層で管理する。

**Test Specification（テスト仕様）**

- 同じ目的、対象機能、テストレベル、操作手順、テスト設計技法を共有するTest Caseをまとめる単位
- `FUT-UI001-01-001`、`FIT-DF001-001`、`ST-UC001-001`等のIDを `test_spec_id` として使用する
- 要件、機能、データフロー、ユースケースからのトレーサビリティは原則としてTest Specification単位で管理する

**Test Case（テストケース）**

- 1つの具体的な `test_data` と `input_data` の組合せ、およびその組合せに対する `expected_result` を表す単位
- Test Specification内で `C001`、`C002` 等の `case_id` を付与する
- 実行結果・証跡では `<test_spec_id>-<case_id>` を実行ケースIDとして使用する

例：

```text
FUT-UI001-01-001
├─ C001
├─ C002
├─ C003
└─ C004

実行ケースID：
FUT-UI001-01-001-C001
FUT-UI001-01-001-C002
```

YAMLの具体的な記載形式は [`test-case-schema.md`](./test-case-schema.md) に従う。

### 4.2 テストデータ用語

本標準では、以下の用語を区別する。

| 用語 | 定義 | 例 |
|---|---|---|
| `preconditions` | テストを実行可能にする環境、認証、権限、設定、接続状態等 | 試験環境、申請者ロール、外部IF試験モード |
| `test_data` | Test Caseの実行開始時点ですでに存在するデータまたは状態 | ユーザーマスタ、既存申請、ステータスがSubmittedのトランザクション |
| `input_data` | テスト実行時にテスト対象機能へ与える入力 | 画面入力、入力ファイル、APIリクエスト、関数引数 |
| `expected_result` | `test_data` と `input_data` の組合せに対する期待結果 | 登録成功、エラー、返却値、保存値、状態遷移 |

テスト実行前のセットアップで作成したデータであっても、テスト対象への入力操作を開始する時点ですでに存在している業務データは `test_data` とする。

画面へ入力する値、IFへ送るファイル・メッセージ、関数へ渡す引数等を `test_data` に混在させず、`input_data` として分離する。

期待結果は原則として各Test Caseへ `expected_result` として記載する。

### 4.3 個別条件

本標準における「個別条件」とは、MC/DCにおける原子条件（Atomic Condition）を指し、AND / OR等でそれ以上分解しない、真または偽で評価できる1つの条件をいう。

例：

```text
ユーザーが有効
AND 申請金額が100000円以下
AND 利用停止されていない
```

は、以下の3個の個別条件に分解する。

```text
C1: user.status == ACTIVE
C2: amount <= 100000
C3: user.blocked == false
```

AIは、複合判定式をMC/DCの対象とする場合、個別条件を明示したうえでTest Caseを設計する。

### 4.4 MC/DC

複数の個別条件をAND / OR等で組み合わせた判定式については、原則としてMC/DC（Modified Condition/Decision Coverage）を用いてTest Caseの組合せを選択する。

MC/DCでは、各個別条件について、他の個別条件の真偽を固定した状態で当該条件だけを変化させたときに、判定結果が変化することを確認する。

例：

```text
Decision = C1 AND C2 AND C3
```

| Case | C1 | C2 | C3 | Decision |
|---|---:|---:|---:|---:|
| C001 | true | true | true | true |
| C002 | false | true | true | false |
| C003 | true | false | true | false |
| C004 | true | true | false | false |

この場合、以下の比較で各個別条件の独立影響を確認できる。

```text
C1: C001 ↔ C002
C2: C001 ↔ C003
C3: C001 ↔ C004
```

MC/DCを適用する場合は、Test Specificationに以下を記録する。

- 判定式
- 個別条件
- 各Test Caseにおける個別条件の真偽
- 各個別条件の独立影響を示すCaseペア
- MC/DCを成立させられない場合の理由

業務上または技術上成立しない組合せを、MC/DC達成のために架空の状態として作成してはならない。

### 4.5 境界値分析との併用

MC/DCは「どの条件組合せを選択するか」を決めるために使用し、境界値分析は「条件をtrue / falseにする具体的な値」を選択するために使用する。

数値、日付、文字数、件数等の境界を持つ個別条件については、MC/DCに加えて境界値分析を適用する。

例：

```text
C2: amount <= 100000
```

候補値：

```text
99999   境界直前
100000  境界値
100001  境界直後
```

MC/DCに必要なCaseで境界値・境界直後を利用し、必要に応じて境界直前等を追加Caseとして確認する。

### 4.6 `test_data × input_data` の組合せ削減

Test Case候補は、概念的には以下から生成される。

```text
test_data × input_data
```

候補となる全直積を機械的に実行することを標準とはしない。

複数個別条件から構成される1つの判定式については、MC/DCを第一の組合せ削減基準とする。

さらに、以下を考慮して必要なCaseを追加する。

- 境界値
- 同値クラス
- 明示された業務エラー
- 状態遷移
- 0件、1件、複数件
- 再実行・冪等性
- 仕様上重要なリスク

MC/DCによって選択されなかった全組合せを1件ずつ列挙することは必須としない。

代わりに、候補組合せ数、MC/DCで選択したCase数、追加した境界値Case数、最終選択Case数、および除外方針をTest Specificationへ記録する。

ただし、業務上禁止された組合せ、成立しない組合せ、特別なリスクを持つ除外条件は明示的に理由を記録する。

MC/DCは1つの判定式に含まれる個別条件の独立影響を確認する技法である。判定式を構成しない互いに無関係なデータ分類の直積へ、組合せ削減だけを目的として形式的にMC/DCを適用してはならない。その場合は仕様、同値分割、境界値、リスク等に基づいてCaseを選択し、選択根拠を記録する。

### 4.7 AIによるテスト設計

AIは、テストを生成する際に以下を行う。

1. 承認済み仕様から判定式、個別条件、境界、状態遷移を抽出する
2. `test_data` と `input_data` を分離して候補パターンを定義する
3. 判定式がある場合はMC/DCを適用して必要Caseを選択する
4. 境界値、異常系、状態遷移等の追加Caseを選択する
5. 各Caseへ `expected_result` を仕様根拠とともに設定する
6. 省略した組合せの選択根拠を記録する
7. Playwright等へ自動化する場合、各Caseの実行結果を一意に追跡できるようにする

AIは、期待結果が不足している場合やMC/DCに必要な状態が仕様上成立するか判断できない場合、推測で補完せず確認事項として報告する。

## 5. 機能単体テスト

### 5.1 基本方針

機能単体テストは、1機能がその責務を完結できることを確認する。

画面機能がSharePointへの登録、更新または削除を責務として持つ場合、実際の開発・試験環境用SharePointリストへの処理結果と保存値の妥当性までをテスト対象に含める。

外部機能を呼び出す場合も、1機能として完結する処理範囲に実接続が必要であれば、テスト環境の実接続先を用いて確認する。

### 5.2 期待する網羅

対象機能に適用可能な以下の観点を確認する。

- 正常系
- 異常系
- 未入力、空白、Null相当
- 境界値
- 0件、1件、複数件
- 条件分岐
- 複数個別条件から成る判定式のMC/DC
- 状態遷移
- SharePoint登録・更新・削除
- 外部機能呼出し
- エラー処理
- 再実行
- 二重操作
- 権限不足
- タイムアウト
- リトライ
- 部分失敗

適用しない観点は無理にテストケースを作成せず、`N/A`と理由を記録する。

AIは、対象コードまたは処理経路とテストケースの対応を示す。

### 5.3 Azure Functionsのコード網羅

利用言語のテストフレームワークを使用し、可能な範囲で以下を取得・確認する。

- ステートメントカバレッジ
- ブランチカバレッジ
- 複数個別条件の判定式に対するMC/DC
- 関数・メソッドカバレッジ
- 例外処理
- 入力値の同値分割
- 境界値
- 外部接続の成功・失敗
- タイムアウト
- リトライ
- 冪等性

数値目標を設定していない場合でも、未テストの分岐と理由をAIが説明できることを必須とする。

### 5.4 キャンバスアプリ、Power Fx、User Defined Functionのコード網羅

一般的なソースコードと同等の実行カバレッジを常に取得できるとは限らないため、以下に基づく構文・分岐・状態・副作用の網羅を使用する。

- `If`、`Switch`等の分岐
- 条件式の真・偽
- 複数個別条件の判定式に対するMC/DC
- 正常・異常
- 境界値
- 状態遷移
- 表示・非表示
- 活性・非活性
- SharePointへの副作用
- 画面遷移
- 外部機能呼出し
- エラー処理

実行カバレッジではない場合は、テスト結果にその旨を明記する。

### 5.5 Power Automate、レポート、データ移行等の網羅

以下を基準とする。

- 処理経路
- 条件分岐
- 複数個別条件の判定式に対するMC/DC
- データパターン
- 状態
- 0件、1件、複数件
- 正常・異常
- 再実行
- 部分失敗
- 外部機能との入出力

### 5.6 画面機能の必須観点

- 初期表示
- `OnVisible`実行後の状態
- 入力項目の初期値
- 必須、形式、桁数、範囲等の入力検証
- 表示・非表示
- 活性・非活性
- 画面内の計算・状態変更
- SharePointへの登録、更新、削除
- 保存された列値と件数
- Lookup、Choice、Person列
- 保存成功・失敗後の画面状態
- 二重押下、連続操作、再実行
- 画面遷移と引数
- 共通メソッド、フロー、Functionへの入力値

### 5.7 レポートの必須観点

- 抽出条件
- 検索期間
- 0件、1件、複数件
- 並び順
- グルーピング
- 集計値
- 小計・合計
- 丸め方法
- 日付・数値の表示形式
- 権限による表示範囲
- Excel、PDF等への出力結果
- 元データ件数との照合
- 金額、数量等の合計照合

### 5.8 インターフェースの必須観点

- 送信または受信の起動条件
- 入力パラメーター
- 送受信メッセージのスキーマ
- 必須項目、データ型、桁数
- 接続元・接続先間のコード値
- 日時、タイムゾーン、文字コード、Nullの扱い
- 正常応答
- 業務エラー応答
- 通信エラー
- タイムアウト
- リトライ
- 再送・再受信
- 冪等性
- 部分失敗
- 認証・認可エラー
- 実行ID、相関ID、ログ
- 接続先環境が正しいこと

### 5.9 バッチの必須観点

- トリガー条件
- スケジュール条件
- 対象データの抽出条件
- 0件、1件、複数件
- 正常処理
- 条件分岐
- エラー処理
- タイムアウト
- リトライ
- 再実行
- 冪等性
- 部分失敗
- 排他・多重起動
- 子フローへの入出力
- 処理件数
- 開始・終了・失敗ログ
- 実行ID、相関ID
- 後続処理の起動条件

**冪等性（べきとうせい）**：同じ処理を同じ条件で複数回実行しても、意図しない重複登録や二重処理が発生せず、業務上の結果が不整合にならない性質をいう。処理のたびに結果を追加することが正しい場合は、その期待動作を仕様へ明記する。

### 5.10 データ移行アプリの必須観点

- 移行元件数
- 移行対象件数
- 移行成功件数
- 移行失敗件数
- 除外件数
- 列マッピング
- コード変換
- 既定値
- Null・空白の扱い
- 日時・タイムゾーン
- Lookup、Choice、Person列の変換
- 不正データの隔離
- 重複データ
- 再実行時の動作
- 移行前後の件数照合
- 金額、数量等の合計照合
- エラー内容と再処理可否

複数の移行先間の関連性は、機能間結合テストで確認する。

### 5.11 共通機能の必須観点

- 通常値
- 最小値・最大値
- 境界値の直前・直後
- 空白・Null相当
- 不正な型または形式
- 想定外の列挙値
- 例外またはエラー
- 同じ入力に対する再実行

副作用を持たない処理として実装できる場合は、可能な限り純粋関数として設計する。

---

## 6. 機能間結合テスト

### 6.1 基本方針

機能間結合テストは、データまたはメッセージを受け渡す入力機能、データストア・インターフェース、および出力機能から構成される1つの連携経路を対象とする。

例：

```text
入力画面 → SharePointリスト → 一覧画面
入力画面 → SharePointリスト → 帳票
画面 → Power Automate → SharePointリスト → 一覧画面
画面 → Azure Functions関数 → 外部システム
```

結合テスト対象の母数は、DFDまたはデータフロー対応表に定義された実在する連携経路の総数とする。

詳細は [`test-traceability-standard.md`](./test-traceability-standard.md) を参照する。

### 6.2 主な検出対象

- 開発者ごとに異なるSharePointリストへ接続している
- 開発用の代替リストが正式接続先として残っている
- 実リストとスキーマ定義書が一致しない
- 入力機能と出力機能で使用列が異なる
- 列内部名、列型、必須設定が異なる
- Choice値、コード値、Nullの扱いが異なる
- 日時・タイムゾーンの扱いが異なる
- Lookup、Person列の保存形式と利用方法が異なる
- IFの接続元と接続先でメッセージスキーマが異なる

### 6.3 必須確認事項

- 正式な接続先を使用していること
- 入力機能で作成したデータを出力機能が利用できること
- 入力から出力まで同一の業務キーを追跡できること
- スキーマ定義と実データが一致すること
- 保存値、表示値、送受信値が一致すること
- 不要なデータ変換や欠損がないこと
- 更新件数が期待値と一致すること
- 関連リスト間のキーが一致すること
- エラー時に不完全データが残らないこと
- 再実行時に意図しない重複が発生しないこと

UI上の成功表示だけで合格とせず、SharePoint、フロー、Function、外部IF等の実結果を確認する。

---

## 7. システムテスト

### 7.1 基本方針

システムテストは、利用者の業務目的を起点としたユースケース単位で作成する。

以下を一連で確認する。

1. ユーザー、権限、データの準備
2. アプリへのサインイン
3. 画面操作
4. 入力、確認、登録
5. Power AutomateまたはAzure Functionsの実行
6. SharePointデータの更新
7. 後続画面、履歴、レポートへの反映
8. エラー発生時の利用者への案内
9. テストデータの後処理

シナリオは、可能な限りGiven / When / Then形式で記述する。

### 7.2 必須トレーサビリティ

以下を必須成果物とする。

- ビジネスファンクションチャート
- ユースケース・機能対応表
- ユースケース間依存関係表

変更機能を利用するユースケースだけでなく、当該ユースケースとデータまたは状態の依存関係を持つ前提・後続ユースケースも影響範囲候補へ含める。

---

## 8. 期待結果の情報源

AIは、期待結果を以下の優先順位で決定する。

1. 承認済み業務要件・ユースケース
2. 承認済み基本設計・詳細設計
3. 承認済み業務ルール・データ定義
4. 承認済みテスト仕様
5. 実装コード

実装コードと上位仕様が異なる場合は、実装コードを期待結果の根拠とせず、仕様不一致として報告する。

情報源が不足して期待結果を確定できない場合は、推測で確定せず、確認事項として報告する。

---

## 9. AIによるテスト作成と変更統制

### 9.1 Test SpecificationとTest Case

AIが作成するTest SpecificationとTest Caseは [`test-case-schema.md`](./test-case-schema.md) に従う。

AIは、使用したテスト設計技法、`test_data`、`input_data`、各Caseの `expected_result`、対象コード・分岐・データフロー、適用しない観点と理由を記録する。

MC/DCを適用する場合は、判定式、個別条件、各Caseの真偽、独立影響を示すCaseペアを記録する。

### 9.2 AIが行ってはならないこと

- 仕様にない期待結果を確定する
- テストを通すために業務仕様を変更する
- テストを通すためにエラー処理を削除する
- 失敗したテストを理由なく無効化する
- 固定待機時間を増やすだけで不安定なテストを隠す
- 本番環境へ無承認でテストデータを作成する
- 本番データを更新・削除する
- 機密情報をテストコードへ記載する
- 失敗結果を成功として扱う

### 9.3 AIによる変更統制

AIがテスト対象コードとテストコードを同時に変更した場合、以下をPull Requestへ明記する。

- 実装変更
- テスト変更
- 期待結果の変更
- 期待結果変更の根拠となる要件・仕様
- AIが置いた前提・推測

AI自身が生成・変更したテストを、AI自身の判定だけで承認済みとして扱わない。

期待結果を変更する場合は、関連要件、仕様、変更理由を必ず記録する。

PoCおよび原因調査で必要な場合は、以下も保存する。

- 使用したAIモデル
- AI指示ファイルのバージョン
- 入力した仕様のバージョン
- テスト生成時のGitコミットID
- 実行したタスクまたはプロンプト

---

## 10. 変更影響分析とリグレッションテスト

### 10.1 影響範囲

AIは以下の4方向から影響候補を抽出する。

1. 直接変更された機能・コード・SharePoint列
2. 変更機能の呼出し元・呼出し先
3. 同一データフロー経路の入力機能・出力機能
4. 変更機能を利用するユースケースと、データ・状態依存を持つ前提・後続ユースケース

詳細は [`test-traceability-standard.md`](./test-traceability-standard.md) を参照する。

### 10.2 リグレッションテスト

#### スモークテスト

- アプリ起動
- サインイン
- 主要画面表示
- 主要業務の正常系
- 主要なSharePoint登録
- 重大な権限制御

#### 変更影響テスト

- 変更機能の機能単体テスト
- 影響するデータフロー経路の機能間結合テスト
- 影響するユースケースのシステムテスト
- 前提・後続ユースケースのうち、データまたは状態依存を持つシナリオ

#### フルリグレッションテスト

- 全機能単体テスト
- 全機能間結合テスト
- 主要または全システムテスト
- 必要な手動確認

AIが選択したテストだけに依存せず、重要シナリオは変更内容に関係なくスモークテストとして実行する。

---

## 11. 不安定なテスト

同一コードに対して成功・失敗が不規則に変化するテストを、不安定テストとして管理する。

記録項目：

- 実行ケースID（`<test_spec_id>-<case_id>`）
- 発生頻度
- 所有者
- 原因
- 暫定対応
- 恒久対応期限

単にリトライして成功したことを理由に、初回失敗を無視しない。

テストを一時的に無効化する場合は、理由、所有者、有効期限を記録する。

---

## 12. SharePointテストデータと環境同等性

### 12.1 スキーマ確認

テスト実行前に、対象SharePointリストのスキーマが期待する定義と一致することを確認する。

確認対象：

- リスト内部名
- 列内部名
- 列型
- 必須設定
- Choice値
- Lookup先
- Person列の複数選択設定
- 添付ファイル設定
- バージョン管理
- アイテム単位権限
- インデックス

### 12.2 テストデータ識別

テスト実行単位で一意な識別子を付与する。

```text
test_run_id = 20260806-123000-abc123
test_spec_id = FUT-UI001-01-001
case_id = C001
execution_case_id = FUT-UI001-01-001-C001
```

### 12.3 事前準備と後処理

- 各Test Caseは、必要な `test_data` をテスト対象への入力開始前に準備する
- `input_data` はテスト対象への操作・呼出し時に与える
- 他のTest Caseが作成した業務データへ依存しない
- 成功・失敗にかかわらず後処理を実行する
- 削除条件は `test_run_id` 等で限定する
- 他テストまたは手動作成データを削除しない

### 12.4 並列実行

- テストごとに一意な業務キーを使用する
- 同じレコードを複数テストで更新しない
- 共通マスタを変更しない
- 順序依存のテストを作らない

## 13. UI自動テスト標準

### 13.1 セレクター優先順位

1. Power Platform Playwright ToolkitのPage Objectまたはヘルパー
2. `data-control-name`
3. AccessibleLabel、role、ARIA属性
4. 安定したその他の属性
5. 表示文言
6. DOM階層、CSSクラス、XPath

DOM階層、CSSクラス、XPathへの依存は原則禁止する。

AccessibleLabelは利用者向けの意味を優先し、テストを安定させるためだけに固定しない。

### 13.2 Page Object Model

画面ごとにPage Objectを作成し、以下を定義する。

- 画面固有セレクター
- 画面読込待機
- 入力操作
- ボタン操作
- 表示値取得
- エラー取得
- 画面固有の業務操作

テストシナリオへ複雑なセレクターを直接記述しない。

### 13.3 待機処理

`waitForTimeout()` 等の固定待機は原則として使用しない。

以下を待機条件とする。

- 対象コントロールの表示
- 処理中表示の非表示
- 画面状態の変更
- SharePointレコードの作成・更新
- フローまたはFunctionの完了状態
- エラー表示

固定待機が必要な場合は、理由と根拠を記録する。

### 13.4 テストの独立性

各テストは単独・順不同で実行可能とする。

認証情報の再利用は許容するが、業務データと画面状態はテストごとに初期化する。

### 13.5 認証状態と秘密情報

以下をGitへ保存しない。

- ユーザー名、パスワード
- Client Secret
- 接続文字列
- アクセストークン
- PlaywrightのstorageStateファイル
- 認証済みブラウザーセッション
- 証明書ファイル、証明書パスワード
- 個人情報、本番データ

環境変数、GitHub Secrets、Azure Key Vault等で管理する。

テストアカウントは役割別に分ける。

```text
test_general_user
test_readonly_user
test_approver
test_unauthorized_user
```


### 13.6 YAML Test SpecificationからPlaywrightへの展開

YAMLのTest Specificationは、Playwrightが直接実行する形式ではない。

AIは [`test-case-schema.md`](./test-case-schema.md) に従ってYAMLを読み取り、各Test CaseをPlaywrightのTypeScript / JavaScriptへ変換する。

原則として、Playwrightの実行結果から以下を一意に特定できるようにする。

- `test_spec_id`
- `case_id`
- 実行ケースID `<test_spec_id>-<case_id>`

AIが複数Caseをパラメータ化テストとして実装することは許容する。ただし、1件の失敗がどのCaseの失敗か判別できない実装は不可とする。

YAMLの `test_data` はテスト開始前のセットアップ、`input_data` はテスト対象への操作・呼出し、`expected_result` はPlaywrightまたは補助検証処理のassertionへ対応させる。

## 14. テスト証跡と結果

自動テストでは、必要に応じて以下を保存する。

- 実行日時
- 実行環境
- アプリバージョンまたはGitコミットID
- Test Specification ID
- Case ID
- 実行ケースID
- 成否
- 実行時間
- エラーメッセージ
- スクリーンショット
- Playwrightトレース
- 動画
- SharePoint検証結果
- Power AutomateまたはAzure Functionsの実行ID
- テストデータ識別子

失敗原因は以下へ分類する。

- 仕様不一致
- 実装不具合
- テストコード不具合
- テストデータ不備
- 環境不備
- 権限不備
- 一時的な通信・サービス障害
- 判定不能

判定できない場合は推測を事実として記載しない。

開発・試験環境には本番データを投入しないため、通常の証跡へ本番データは含まれない前提とする。

例外的に本番環境でテストした場合は、証跡のアクセス制限、マスキング、保存期間、削除期限を設定する。

## 15. テスト実施タイミング

### 15.1 コード生成・Pull Request時

1回の実行で以下を組み合わせる。

- 変更機能の機能単体テスト
- 影響するデータフロー経路の機能間結合テスト
- 主要ユースケースのスモークテスト

### 15.2 試験環境デプロイ後

- 変更機能の機能単体テスト
- 影響する全機能間結合テスト
- 影響するシステムテスト
- 常時実行する主要業務シナリオ

### 15.3 夜間・定期実行

- 全機能単体テスト
- 全機能間結合テスト
- 主要システムテスト

### 15.4 リリース前

- 全機能単体テスト
- 全機能間結合テスト
- 全システムテスト
- 手動確認対象

---

## 16. 完了条件

- Test Specificationが作成され、1件以上のTest Caseが定義されている
- 対象要件、機能、データフロー、ユースケースとの対応が記録されている
- `test_data`、`input_data`、各Caseの `expected_result` が区別されている
- 正常系、異常系、境界値が含まれている
- 複数個別条件の判定式へMC/DCを適用した場合、各個別条件の独立影響を示すCaseペアが記録されている
- MC/DC適用不能な条件がある場合、理由が記録されている
- 対象コード・処理経路とTest Specification / Test Caseの対応が説明されている
- 自動化対象と判定したテストが自動化されている
- 自動化しないテストの理由、実施時期、責任者が記録されている
- SharePoint上のデータ結果が確認されている
- すべての必須テストが成功している
- 未解決の失敗・保留事項が記録されている
- テスト証跡が保存されている
- テストデータが後処理されている
- 変更時は必要なリグレッションテストが実行されている

## 17. 自動化対象の判断基準

以下を考慮して自動化対象を決定する。

- 実行頻度
- 業務影響
- リグレッションの重要性
- 自動化の安定性
- テストデータ準備の難易度
- 実装・保守コスト
- 人間による目視判断の必要性
