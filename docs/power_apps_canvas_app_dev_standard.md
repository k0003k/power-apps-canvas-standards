# Power Apps キャンバスアプリ開発標準

作成日：2026-06-24  
改訂：2026-08-06（開発標準を分割し、AI自動テストを可能にする実装標準を追加）

## 0. 目的・適用範囲

本標準は、Power Apps キャンバスアプリを、保守しやすく、読みやすく、実装者間で迷いにくく、AIによるコード生成・レビュー・自動テストを行いやすい形で作成するための最低限の開発標準である。

前提は以下とする。

- モダンコントロールを主に使用する
- SharePointリストを主要データソースとして使用する
- 固定の `X` / `Y` 指定は極力使用しない
- コンテナベースでレイアウトを構成する
- レスポンシブ対応は必須としない
- 独自定義要素は snake_case を基本とする
- 標準関数はPower Fx標準のCamelCaseに従う
- 開発環境、試験環境、本番環境を分離する

本標準から外れる場合は、理由、代替策、影響範囲を説明できることを条件とする。

関連標準：

- [命名規則](./naming-conventions.md)

- [テスト・トレーサビリティ標準](./test-traceability-standard.md)
- [テストケース定義](./test-case-schema.md)

## 1. レイアウト標準

### 1.1 基本方針

画面構成はコンテナベースで設計する。  
固定の `X` / `Y` 座標を直接指定する実装は、原則として避ける。

モバイルアプリの場合、ベースサイズはアプリ設定に従う。  
実機ではスケール表示される前提で、画面内の配置はコンテナを使って調整する。

リキッドレイアウトは初期標準では必須としない。  
まずは、画面全体が端末サイズに応じて拡大・縮小される構成を標準とする。

### 1.2 基本構造

画面は、原則としてルートコンテナを起点に構成する。

```text
root_capture
└─ main_capture
   ├─ header_capture
   ├─ body_capture
   └─ footer_capture
```

画面内の要素は、原則として以下の単位でコンテナ化する。

- ヘッダー
- メインコンテンツ
- 入力エリア
- ボタンエリア
- フッター
- モーダル・確認エリア
- 一覧・カード・明細エリア

### 1.3 固定座標の扱い

`X` / `Y` の直接指定は、原則として使用しない。

位置調整は、以下を優先する。

- コンテナ
- パディング
- ギャップ
- マージン相当の空白コンテナ
- Align / Justify などの配置プロパティ

ただし、コンポーネント内部や装飾目的で厳密な重ね合わせが必要な場合は、限定的に `X` / `Y` 指定を許容する。

### 1.4 垂直・水平・通常コンテナの使い分け

垂直コンテナは、上から下に積む構造に使用する。

```text
例：
header / body / footer
カード内のタイトル / 本文 / ボタン
```

水平コンテナは、左から右に並べる構造に使用する。

```text
例：
戻るボタン / タイトル
アイコン / ラベル
ボタン横並び
```

通常コンテナは、重ね合わせや自由配置が必要な場合に使用する。

```text
例：
画像の上にラベルを重ねる
カードを浮いているように見せる
独自の進捗部品を作る
```

### 1.5 幅・高さ・余白

画面全体で使用する基本幅、高さ、余白は、可能な限り Named Formula または共通定義として管理する。

```powerfx
base_screen_width = 390
base_margin = 16
base_header_height = 56
base_footer_height = 72
base_button_height = 44
```

固定値を各コントロールに直接散らばらせない。  
後から画面サイズ、余白、ボタン高さなどを一括変更できる状態を維持する。

### 1.6 コンテナの伸縮設定

同一階層に配置するコンテナでは、伸縮可能なコンテナは原則1つのみとする。

縦方向コンテナの場合は「高さ（伸縮可能）」、横方向コンテナの場合は「幅（伸縮可能）」を対象とする。

画面全体を `header / body / footer` のように分割する場合は、固定領域と可変領域を明確に分ける。

```text
header_capture：高さ固定
body_capture  ：高さ（伸縮可能）オン
footer_capture：高さ固定
```

同一階層で複数のコンテナを伸縮可能にすると、余白の配分やスクロール位置が読みづらくなり、画面改修時にレイアウト崩れが発生しやすくなる。  
そのため、伸縮可能なコンテナは、原則として「残り領域を受け持つ主領域」に限定する。

例外として、同一階層内で複数領域を意図的に比率配分したい場合のみ、複数の伸縮設定を許容する。

```text
例：
左右2ペインを可変幅で表示する
上下2領域を同じ比率で表示する
複数のカード領域を画面サイズに応じて均等配分する
```

例外として複数の伸縮設定を使用する場合は、各コンテナの役割と期待する表示比率を設計メモまたはコメントで明確にする。

### 1.7 ヘッダー・ボディ・フッター

ヘッダーとフッターは固定高さとし、ボディを可変領域とする。

モバイル画面を `640 x 1136` ベースで設計する場合、目安は以下とする。

```text
header_capture：80〜120
footer_capture：80〜120
body_capture  ：残り領域
```

ボタンやナビゲーションが多い場合は、フッターをやや大きめにする。

### 1.8 「いっぱいに広げる」オプション

幅・高さを明示的に制御するため、`いっぱいに広げる` オプションは原則として使用しない。

理由は以下とする。

- 意図しないサイズ変更が発生しやすい
- 他要素との関係が読み取りにくくなる
- 修正時に影響範囲を予測しづらくなる
- AIや第三者がレイアウト意図を判断しづらくなる

## 2. UI/UX 標準

### 2.1 導線

画面上の導線は、原則として左から右、上から下とする。  
対象ユーザーが日本語・英語など左から右に読む文化圏であることを前提とする。

### 2.2 操作目的と画面構造

利用者が「何をしたいか」と「どこで何ができるか」が紐づきやすいレイアウト・画面遷移とする。

特に以下を意識する。

- 主要操作は視認しやすい位置に置く
- 入力、確認、保存、戻るなどの流れを自然にする
- 同じ意味の操作は、画面間で位置、色、文言をそろえる
- 危険操作は通常操作と視覚的に分離する

### 2.3 操作結果の明示

利用者が操作する要素には、操作後に何が起きるか分かる命名、アイコン、色、アニメーションを採用する。

良い例：

```text
保存
申請する
削除
再読み込み
承認
差戻し
キャンセル
```

曖昧な表現は避ける。

避ける例：

```text
OK
実行
処理
次へ
完了
```

ただし、文脈上明らかな場合は使用してよい。

### 2.4 通知・メッセージ

時間がない場合は `Notify` を使用してよい。  
ただし、重要なエラー、確認、業務判断を伴うメッセージでは、可能な限りインタラクティブな表示を使用する。

標準方針は以下とする。

| 種別 | 表示方法 |
|---|---|
| 軽微な完了通知 | `Notify` |
| 入力エラー | 画面内メッセージ |
| 保存失敗 | 画面内メッセージまたはモーダル |
| 削除・取消などの危険操作 | 確認ダイアログ |
| 業務判断が必要な警告 | モーダルまたは専用エリア |

### 2.5 カラー

色は意味を持たせて使用する。  
装飾目的だけで色を増やさない。

| 色 | 意味 |
|---|---|
| 赤 / 黒 / 紫 | 最重要、深刻、危険、不可逆操作 |
| 黄 / オレンジ | 注意、警告、確認が必要 |
| 青 / グリーン | 通常、成功、進行、肯定的操作 |
| 白 / グレー | ベース、背景、通常表示 |

企業ブランドカラーがある場合は、ブランドカラーを優先する。  
その場合も、意味ごとの色分けは補色、濃淡、アクセントカラーで再設計する。

ナイトモードは将来的な対応候補とし、初期標準では対象外とする。

## 3. カード表現

Power Apps の標準カードにこだわらず、コンテナでカード風の部品を作成してよい。

カード風コンテナでは、以下を設定する。

- 背景色
- 角丸
- 余白
- 必要に応じた影や境界線

```text
例：
application_summary_card
capture_guide_card
result_detail_card
```

カード内は、さらに垂直コンテナや水平コンテナをネストして構成する。

## 4. コンポーネント化方針

複数画面で再利用する部品、または単独で意味を持つ複雑な表示部品は、コンポーネント化を検討する。

```text
例：
進捗ステッパー
共通ヘッダー
共通フッター
検索条件ブロック
エラーメッセージ表示
```

特に、円とバーを組み合わせる進捗表示のように、コンテナだけでは微調整が難しいものは、コンポーネント化した方が保守しやすい。

コンポーネント化する場合は、入力プロパティ、出力プロパティ、責務を明確にする。  
単に見た目だけをまとめるための過剰なコンポーネント化は避ける。

## 5. データ操作標準

### 5.1 Form / Patch の使い分け

フォームで実現できる登録・更新処理は、原則としてフォームを使用する。

`Patch` は以下の場合に限定する。

- 複数レコードを一括更新する
- フォームでは表現しづらい更新制御がある
- 楽観ロックや業務ルールを明示的に制御する
- 更新対象を動的に切り替える必要がある

単純な登録・更新で `Patch` を多用しない。

### 5.2 保存後処理

保存成功後、失敗後、キャンセル時の処理を明確に分ける。

保存後も同じ画面に残る仕様の場合は、保存後に画面上の基準値、選択レコード、Modified 相当の比較値などを更新する。  
古い比較値を保持したまま再保存しない。

### 5.3 エラーハンドリング

データ操作では、利用者にとって意味のあるエラーメッセージを表示する。

技術的なエラー内容をそのまま表示するのではなく、利用者が次に何をすればよいか分かる表現にする。

## 6. 状態管理標準

### 6.1 `App.OnStart` に多くの処理を詰め込まない

`App.OnStart` に初期化処理を詰め込みすぎない。

現在の Power Apps では、非ブロッキング `App.OnStart` が標準的な動作である。  
また、非ブロッキング動作を無効化する設定は廃止済みに分類されているため、当該設定に依存した設計は行わない。

そのため、`App.OnStart` で初期化した変数・コレクションが、スタート画面の `OnVisible` や各コントロールから即時参照される前提の実装は避ける。

理由は以下とする。

- `App.OnStart` と画面側処理の実行順序が保証されない場合がある
- 非ブロッキング `App.OnStart` が有効な場合、`App.OnStart` と `Screen.OnVisible` は並行して実行され得る
- `App.OnStart` で初期化した変数・コレクションを参照すると、初期化前の値を参照するリスクがある
- 初期化処理の依存関係が見えにくくなり、保守時の原因調査が難しくなる

`App.OnStart` は、アプリ全体で一度だけ必要な軽量な初期化に限定する。  
画面表示に必要な値は、画面単位の `OnVisible`、Named Formula、または必要箇所での遅延評価に寄せる。

### 6.2 変数の使い分け

グローバル変数は、アプリ全体で共有する状態に限定する。

ローカル変数は、画面内だけで完結する一時状態に使用する。

Named Formula は、読み取り専用の計算値、参照値、共通定数に使用する。

処理の再利用には、User Defined Function を使用する。

## 7. Power Fx 実装標準

### 7.1 `With` の過剰ネスト

`With` のネストは原則として避ける。

- 1層目：許容
- 2層目：非推奨
- 3層目以上：強く非推奨

`With` をネストする前に、以下を検討する。

- `As` 句で読みやすくできないか
- Named Formula に分離できないか
- 変数またはコレクションに分けた方がよいか
- User Defined Function に切り出せないか
- 処理をコンポーネント側に寄せられないか

### 7.2 `If` の過剰ネスト

`If` のネストは原則として避ける。

- 1層目：許容
- 2層目：非推奨
- 3層目以上：強く非推奨

複数条件の分岐は、可能な限り `Switch`、条件判定用の Named Formula、または User Defined Function に分離する。

### 7.3 `!IsBlank()` の乱用

単純な代替値の指定には、`!IsBlank()` ではなく `Coalesce()` を優先する。

```powerfx
Coalesce(input_value, default_value)
```

ただし、空白かどうか自体を判定したい場合は `IsBlank()` を使用してよい。

### 7.4 否定条件の乱用

条件式で `!A_status` や `Status <> "A"` のような否定条件を安易に使用しない。

複数ステータスが存在する場合は、原則として対象ステータスを列挙する。

```powerfx
Status in ["B", "C"]
```

理由は以下とする。

- 将来 `D` が追加された場合に、意図せず対象に含まれるリスクがある
- 読み手が全ステータスを完全に把握しているとは限らない
- 条件の業務意図が伝わりにくい
- コンボボックスの `Default` / `DefaultSelectedItems` 系プロパティで使用した場合、参照先データや初期値の評価タイミングによって、想定どおり選択状態が復元されないことがある

否定条件は、全体集合が明確で、将来追加される値も含めて意図的に「A以外」としたい場合のみ使用する。

### 7.5 コピペ実装

同じような処理を3回コピーする前に、関数設計、部品化、共通化を検討する。

検討順序は以下とする。

1. User Defined Function で共通化できないか
2. Named Formula で読み取り専用値として共通化できないか
3. コンポーネント化できないか
4. コレクションや設定テーブルで制御できないか
5. 画面構造や処理配置を見直せないか

理想は、実装前に以下を設計しておくことである。

- User Defined Function
- Named Formula
- コンポーネント
- 画面ごとの責務
- 機能ごとの処理配置

### 7.6 委任可能な設計

以下のルールに沿い、委任可能な設計を原則必須とする。

- データソースに対する検索、絞り込み、並び替えは、委任可能な関数および演算子を利用すること
- 委任警告（黄色下線）が表示される数式は、原則としてリリース前に解消すること
- 大量データを扱う画面は、データソース側で処理可能な設計を優先すること
- SharePoint、Dataverse、SQL Server 等のデータソースごとの委任制約を考慮して実装すること

※委任できない数式は Power Apps クライアント側で評価されるため、取得件数上限の影響を受け、データ量の増加に伴い検索結果の欠損や性能低下を引き起こす可能性がある。

## 8. 自動テストを可能にする実装標準

### 8.1 基本方針

アプリは、PlaywrightおよびAIが画面を安定して操作し、処理完了と期待結果を機械的に判定できるように設計する。

詳細なテストレベル、テストケース、環境、証跡、回帰テストの標準は [`testing-standard.md`](./testing-standard.md) を参照する。

### 8.2 画面の機能単位

1つの `Screen` オブジェクトを、原則として1つの画面機能として扱う。

画面が複数の独立した業務目的を持つ場合は、画面分割または画面内機能の責務分離を検討する。

### 8.3 テスト対象コントロール

以下のコントロールは、必ず命名規則に従って明示的に命名する。

- 画面読込完了の判定に使用するコントロール
- 入力コントロール
- ボタン、アイコン等の操作対象
- 期待結果を表示するラベル
- Gallery
- Form
- モーダル
- エラーメッセージ
- 処理中表示
- 完了表示

コントロール名はアプリ全体で一意とし、Playwrightの `data-control-name` による識別に利用する。

### 8.4 AccessibleLabel

利用者が操作するコントロールには、目的を表すAccessibleLabelを設定する。

AccessibleLabelはアクセシビリティを目的として設定し、自動テスト専用の不自然な値を設定しない。

自動テストのセレクターでは、原則として `data-control-name` をAccessibleLabelより優先する。

### 8.5 画面読込完了の判定

各画面は、自動テストが読込完了を判定できる状態を持つ。

以下のいずれかを利用する。

- 対象画面固有の主要コントロールが表示される
- 処理中表示が非表示になる
- 画面状態を示すコントロールが表示される
- 必要なSharePointデータがGalleryへ反映される

固定秒数の待機だけで読込完了を判定しない。

### 8.6 非同期処理の状態

Power Automate、Azure Functions、SharePointへの反映等の非同期処理は、完了状態を機械的に確認できる設計とする。

必要に応じて以下を保持する。

- 処理状態
- 処理結果
- 実行ID
- 相関ID
- 完了日時
- エラーコード
- エラーメッセージ

### 8.7 ロジックと副作用の分離

判定、計算、変換等のロジックと、SharePoint更新、画面遷移、通知等の副作用は可能な限り分離する。

再利用可能な判定・変換ロジックは、User Defined Functionまたはテスト可能な外部メソッドへ分離する。

### 8.8 SharePoint接続先とスキーマ

画面、フロー、Azure Functions、レポート、移行アプリは、環境ごとに承認されたSharePoint接続先を使用する。

開発者が独自に作成した代替リストを、正式な機能単体テストまたは機能間結合テストの接続先として使用しない。

対象リスト、列内部名、列型、Choice値、Lookup先等は、承認済みのスキーマ定義と一致させる。

### 8.9 エラーの観測可能性

エラーを握りつぶさず、利用者とテストが少なくとも以下を確認できる状態にする。

- 処理が失敗したこと
- 再操作が可能か
- 必要に応じて問い合わせに利用できる実行IDまたは相関ID

機密情報、内部例外、接続情報を画面へ直接表示しない。

## 9. 非推奨事項 / Don’ts

以下は、保守性、可読性、実行順序、将来変更および自動テストへの耐性を下げやすいため、原則として避ける。

| 非推奨 | 代替方針 |
|---|---|
| `App.OnStart` に多くの処理を詰め込む | 画面単位の `OnVisible`、Named Formula、遅延評価に寄せる |
| 単純更新で `Patch` を多用する | Form / SubmitForm を優先する |
| `With` を深くネストする | `As`、Named Formula、User Defined Functionに分離する |
| `If` を深くネストする | `Switch`、判定式、User Defined Functionに分離する |
| `!IsBlank()` で代替値を制御する | `Coalesce()` を使用する |
| `Status <> "A"` のような否定条件を多用する | 対象値を列挙する |
| 同じ処理を何度もコピペする | 3回目の前に共通化する |
| 固定の `X` / `Y` に依存する | コンテナ、余白、配置プロパティを使う |
| 画面ごとに色や文言を変える | 意味ごとの色、文言、位置を統一する |
| Named Formulaを関数のように扱う | User Defined Functionを使用する |
| 委任不可の数式を安易に採用する | 委任可能な実装を再検討する |
| テスト対象コントロールにデフォルト名を使用する | アプリ全体で一意な意味のある名前を付与する |
| 表示文言だけでUI要素を特定する | `data-control-name`を優先し、Page Objectで吸収する |
| 固定時間待機に依存する | 表示状態、処理状態、データ更新を条件として待機する |
| 開発者独自の代替SharePointリストで正式テストを完了する | 承認済みの環境別接続先とスキーマを使用する |
| エラーを握りつぶす | 利用者向け状態と調査用IDを残す |

## 10. 実装時の判断基準

迷った場合は、以下の順で判断する。

1. 後から見て役割が分かるか
2. 画面構造をツリーで見たときに理解しやすいか
3. 固定座標に依存しすぎていないか
4. 変更時に影響範囲が局所化されているか
5. コントロール名がアプリ全体で一意か
6. 命名が長すぎず、短すぎないか
7. AIや第三者が意図を誤解しにくいか
8. 自動テストから安定して操作・判定できるか
9. SharePoint上のデータ結果を機械的に確認できるか
10. データフローとユースケースへの影響を追跡できるか

本標準は、過剰な抽象化よりも、実装者が迷わず作れることを優先する。  
迷った場合は、短く書くことよりも、誤解されにくく書くことを優先する。
